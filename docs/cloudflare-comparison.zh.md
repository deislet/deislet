# 功能性评审：Deislet 对照 Cloudflare Workers / Pages

日期：2026-08-31。对照的代码是 `3753cb2`。

这份评审第一次写出来时对照的是 `fea1ab8`。之后四个提交改动了它的结论，全文按新代码逐条重核过：
`38fbeda`（静态站点规则、目录路由、数据面 CLI、调用轨迹、CPU 上限）、`1be047c`（把六个「写好了但没有调用点」的功能接到真实请求路径上）、`b149c42`（前门升到 pingora 0.8.1）、`3753cb2`（离开 deno 分支，改用发布版 deno_runtime 0.266）。第 6 节末尾列了这四个提交各自关掉了什么。

## 0. 这份评审的口径

Deislet 的定位是**私有化部署的小平台**：一个机房、几台机器，没有全球任播网络，没有几百个边缘节点。所以「我们节点少」不算差距——那是定位本身。这份评审只问一件事：

> 一个开发者按 Cloudflare Workers 的写法写好的应用，搬到 Deislet 上，**哪些地方会写不出来、跑不对、或者运维接不住**？

判定分三档：

- ✅ 有，且经代码核实
- ⚠️ 有一半，缺的部分写明
- ❌ 没有

每一条 Deislet 侧的判定都对着代码核过，不是按文档。这一点必须强调，因为这个仓库反复出现过「文档声称的能力代码里没有」——最初那一轮就修了十几处，之后又出现过反过来的一种：功能写好了、测试也有，但**没有任何一条真实请求能走到它**（`1be047c` 一次性接上了六个这样的功能）。所以判 ✅ 的门槛是「从外面打一发请求能用到」，不是「代码里有这个函数」。

---

## 1. 结论

第 2 节那八张表一共 75 行：**✅ 49、⚠️ 5、❌ 21。**

21 个「没有」里，绝大多数分成两堆：一堆是 **Cloudflare 在卖它自己的机器**（Workers AI、Vectorize、Hyperdrive 之类），自建装机缺的是硬件不是平台功能；另一堆是**多接入点网络才有的属性**（第 3 节列了 11 项）。剩下**8 项是自建用户真会撞上的**，第 4 节逐条展开；第 4 节末尾另收了四条「有一半」的，每条缺的都太小，不够单开一条。

按撞上的概率和痛感排，前五个是：

1. **流式响应过不了 isolate 边界** —— Server-Sent Events 写不出来，大文件代理会整个进内存
2. **没有 Durable Objects 或任何协调原语** —— 计数器、锁、房间、在线状态，一个都做不了
3. **对象存储只有 put/get/delete** —— 不能列举、不能断点续传、不能按字节范围取
4. **没有账号体系** —— 一把 API key 通吃所有应用的所有操作，第二个人加进来就没法分权
5. **证书要人手放、人手续** —— 每加一个域名都要运维介入，续期忘了就是线上事故

后面还有三条，第 4 节逐条展开。

需要说明的是：这个清单是**几轮修完之后**的清单，比第一稿短了不少。第一稿的前五名里有三条（`waitUntil` 不受限、没有事务、请求体没有上限）在评审那一轮就修掉了，还顺带修掉了一个跨租户读写数据库的严重漏洞；随后又关掉了五条——静态站点规则、控制面路由接到前门、数据面 CLI、按次调用的轨迹与延迟分位数、CPU 时间上限。第 6 节列了这两批各自做了什么。

## 3. 因为是单集群，所以本来就不需要的

这 11 项不是差距，列出来是为了避免后来者把它们误当成待办：

- **灰度百分比放量**。CF 需要它是因为一次变更同时落到几百个机房，得有统计意义的爬坡。这里部署只到少数几台机器，回滚是挪指针、一秒完成，「蓝绿 + 秒级回滚」在这个规模上覆盖了同样的需求。（如果机队真长到几十台，按节点分批仍然值得做；按百分比那套机器不值得。）
- **Smart Placement / 区域放置提示**。只有一个地方能跑，没什么可决定的。
- **任播、全局负载均衡、地理调度、Argo**。都是多接入点网络的属性。
- **Tiered Cache / Cache Reserve**。它们存在是为了减少跨机房回源。这里源站就在旁边。
- **Durable Object 的司法辖区与位置提示**。运维已经选好机器在哪了。
- **Workers for Platforms / dispatch namespace**。那是「大规模托管别人的不可信 Worker 并计费」的产品。自建装机真正需要的那部分是 RBAC，已单列为真实缺口。
- **免费版 / 付费版的限额分层与账号级日配额**。没有计费套餐要区分。
- **多区域存储复制与只读副本**（D1 read replication、R2 jurisdictions）。单集群没有意义；单集群内为了可用性做复制是另一回事，已单列为真实缺口。
- **Workers AI 与 Vectorize 作为一等绑定**。这两个是 CF 在卖自己的 GPU 机队和索引服务。自建用户通过 `fetch` 调外部推理 API 今天就能用，而且我们的出站策略让这个调用是受管控的。缺的是硬件，不是平台功能。
- **Hyperdrive 的全球连接池层**。它的价值是在每个机房旁边握着热连接，免得悉尼的 Worker 现开一条到弗吉尼亚的 Postgres 会话。单集群里数据库就在同一个局域网。

## 4. 真正要紧的缺口

按「自建用户撞上的概率 × 撞上之后有多难受」排序。每条给出：现象、后果、今天只能怎么办、大致代价。

编号保持不变，**已经关掉的五条也留在原位**，写清做了什么——因为第 7 节的排序是按这些编号说话的，一条缺口悄悄消失，读排序的人会以为自己漏看了。

### 4.1 流式响应过不了 isolate 边界

**现象**：`ReadableStream` / `WritableStream` / `TransformStream` 三个构造器都在，handler 内部用它们完全正常。但请求体和响应体在跨 Rust↔JS 边界时是**一整块完整的字节数组**（`isolate.rs` 的 `PendingRequestBody` / `PendingResponseBody`）。

**后果**三条，一条比一条难受：

1. **Server-Sent Events 写不出来**。SSE 的做法是返回一个永不结束的响应体，一条条往外推。这里 handler 必须先把整个响应体凑齐才能返回，所以推不出去。任何「实时进度条」「流式 AI 回答」都得改用 WebSocket 绕。
2. **代理大文件会整个进内存**。`return fetch("https://.../big.iso")` 会把整个文件读进节点内存再吐出去。有了评审那一轮加的内存上限，这不会再撑爆节点了——但会变成这个应用自己被杀掉。
3. **最阴的一条**：因为三个构造器都在，照着流写的代码**能编译、能跑、行为却是错的**——它不报错，只是不流。

**今天只能怎么办**：分块下载 + WebSocket 推送，或者把大文件直接放静态资源让 asset-first 那条路服务（那条路是流式的）。

**大致代价**：中到大。要把 op 边界从「一块字节」改成「一个可读资源」，`deno_core` 有 `ResourceId` 这套东西可以用；但 dispatcher、pool、isolate 三层的消息类型都要跟着改，Cache API 和 KV 也要想清楚要不要跟。

### 4.2 没有 Durable Objects，也没有任何协调原语

**现象**：没有任何东西能保证「同一个键的操作被串行地、在同一个地方执行」。

**后果**：一整类东西做不了——串行计数器、分布式锁、每实体状态机、多人协作 / 房间、跨连接的 WebSocket 在线名册。

这一条**不是单集群的后果，恰恰相反**：单集群是最容易做单实例 actor 的地方，不需要任何全局路由。

**今天只能怎么办**：交互式事务（评审那一轮新增）能覆盖「读—判断—写」这一类；剩下的没有替代。

**大致代价**：大。要有对象标识到节点的路由、每对象的单线程执行、每对象的持久状态，以及一个应用调用另一个对象的调用路径。

### 4.3 对象存储只有 put / get / delete

**现象**：`blob.proto` 就三个方法，`GetRequest` 只带一个 key。

**后果**：不能翻页列举一个桶、不能按字节范围取（所以视频拖动进度条不行、大文件断点续传不行）、不能做条件写（compare-and-set）、不能挂自定义元数据。对自建用户来说，这是「对象存储」和「一个你必须已经知道名字才能取的地方」之间的区别。

**大致代价**：中。元数据已经在 SQLite 里，list 和 head 主要是加 RPC；range 读要动流式下载那条路（和 4.1 相关）；条件写要一个原子的 compare-and-set。

### 4.4 静态站点缺 `_redirects` / `_headers` / SPA 兜底 —— 已关闭

**当时的现象**：三个都没有。地球上每一个静态站点生成器都会吐 `_redirects` 或 `_headers`，而这个平台是当作「自建版 Pages」宣传的；想给一个静态路径加一条重定向或者加一个 `Cache-Control`，就得写一个函数——这恰好绕开了 asset-first 的全部意义。

**做了什么**（`38fbeda` 做了解析和编译，`1be047c` 把它接到请求上）：

- 格式定义放在 `deis-bundle` 的 `site.rs` / `redirects.rs` / `headers.rs`，编译器和节点共用一份，谁都不独占这个格式。构建时解析，**规则写错就构建失败**，报出文件名、行号和那一行的原文；构建产物里不再带这两个文件本身。
- 节点在装载一版的时候把清单里的文本编译成表，之后每个请求只是查一次哈希、扫一张定长的表。
- 一个请求的判定顺序是：先看资产索引（路径命中文件就是那个文件）→ `_redirects`（按作者写的顺序，首条命中者胜）→ 清单里声明的函数路由（认领了就归 isolate）→ 兜底行为。`_redirects` 排在函数路由**之前**是有意的：作者手写的规则是他做的决定；兜底不是手写的，所以让位。
- `_redirects` 的 200 是改写（地址栏不变、返回目标的字节），404 是带 404 状态返回目标，其余状态是真跳转。跳到站外只允许「真跳转」且主机名必须是常量，改写跳站外一律拒——改写是从**本包**里取字节，允许它跳站外等于让节点按作者给的地址开一条不经出站策略的连接。
- `_headers` 是所有命中的块都生效、靠后的覆盖靠前的（和 `_redirects` 相反，因为头是叠加的、跳转是单个决定）。`! 名字` 只能去掉这些块自己设过的头；节点算出来的 `Content-Type` / `Content-Length` / `ETag` / 默认 `Cache-Control` 去不掉，`x-deis-` 开头的平台头也不许写。
- 兜底行为在项目配置里写 `assets.notFound`：`none`（交给 isolate 自己答 404）、`404-page`（返回 `404.html`，状态 404）、`single-page-app`（返回 `index.html`，状态 200）。不写而包里有 `404.html` 时按 `404-page` 处理。
- 一处刻意的收窄：通配符 `*` 只能当路径的最后一整段，`/*.jpg` 这种段内通配在构建期就拒绝，不做「半懂」。按扩展名设头请把文件放进一个目录再匹配 `/img/*`。

**没做的**：`_redirects` 里没有强制 HTTPS、没有按国家或语言分流这类 Cloudflare 后来加的条件规则。

### 4.5 一种资源只能挂一个绑定，且没有账号体系

两件事，凑在一起说是因为它们都属于「第二个人 / 第二个用途加进来的时候就不够用了」。

**具名绑定**：一个 `(应用, 环境)` 只有一个 KV、一个数据库、一个对象存储、一个默认队列。冷热数据分开、一个应用挂两个桶，没有任何表达方式。（`ServiceConfig` 上的 `namespace` 和 `connectionString` 评审那一轮删掉了——两个字段都在，但全仓没有一个读者，留着是个陷阱：作者能设，没人读。）

**账号体系**：一把扁平的 API key 授予对所有应用的所有操作。第二个人或第二个团队用上这套装机的那一刻，没有任何办法限定范围或者归因，而部署路径上是带着解密后的密钥走的。

**大致代价**：具名绑定中等（要动 manifest、控制面数据模型、绑定注入）；RBAC 中到大。

### 4.6 没有按次调用的轨迹，延迟没有分位数 —— 已关闭

**当时的现象**：`deis tail` 流的是日志行，没有一条记录把「这次请求的地址、状态码、耗时、有没有抛异常」绑在一起。延迟存的是一个只升不降的高水位数值，所以「p99 是多少」回答不了——一次 30 秒的超时会把这个数字永久钉在 30 秒。

**做了什么**（`38fbeda` 产出，`1be047c` 给了读它的人）：

- deis-telemetry 多了一套 `TraceService`：推送、查询、跟随三个调用，和日志那套并排放，不混在一起。
- 节点每处理完一次调用就发一条轨迹——请求、队列批次、cron 触发、WebSocket 消息各算一次——记的是**平台做的判定**，所以「应用自己抛了」和「我们把它杀了」是两种不同的结局，超时、op 限流、内存、CPU 各有各的名字。
- 延迟从高水位改成直方图（`deis_runtime_isolate_execution_ms_bucket`，14 个桶，配 `_sum` 和 `_count`），Prometheus 的 `histogram_quantile` 能直接算分位数。
- 读的一头是 `deis trace`：按结局筛（`--outcome ok/app-error/timeout/rate-limited/memory-limit/cpu-limit/internal-error/failed`）、按类型筛（`--kind http/queue/cron/websocket`）、按状态码或状态码段筛、按时间段、按耗时下限、按轨迹号，也能 `--follow` 跟实时的。轨迹号和 `deis logs --trace-id` 是同一个号，所以从一条轨迹能直接跳到那次调用写的日志。

**半条**：采样有机制，没有配置位。节点默认把成功的调用也全记下来（采样率 1.0），被平台判失败的那些**任何采样率下都不丢**；但采样率和缓冲上限只能用环境变量 `DEIS_TRACE_SAMPLE_RATE` / `DEIS_TRACE_BUFFER` 调，节点的配置文件里没有对应的字段。deis-telemetry 那头留存是有默认的：`trace_retention_days = 3`，比日志的 7 天短，因为不管应用写不写日志，每次调用都会产生一条轨迹。

**没做的**：控制台里没有把这些数字画出来。

### 4.7 没有 compatibility date / flags

**现象**：没有任何机制让一个已部署的版本钉住它当初写作时的运行时语义。

**后果**：将来任何一次全局面或 `Response` 处理的改动，都是**整个机队的破坏性变更，没有渐进通道**。评审那一轮一次性绑了十个全局，如果哪天要收回一个，就没有平滑的办法。

**大致代价**：中。manifest 里加一个日期，isolate 构建时按日期分支。难的不是机制，是从现在开始必须一直守住它。

### 4.8 控制面里的路由没有任何人读 —— 已关闭

**当时的现象**：`/api/routes` 由控制面提供服务，`deis-proxy` 里 grep 不到一处读它，proxy 的域名表是从另一份配置来的。同一个问题（「这个请求该给哪个应用」）有两个真相来源，路径前缀路由和预览子域两件事都卡在这一根没接上的线上。

**做了什么**（`38fbeda`）：

- 控制面另开了一条给数据面用的路径 `/api/routing-table`。它和给控制台看的 `/api/routes` 不是同一个形状：这条带的是环境的**名字**（`production`、`pr-42`，也就是 `x-deis-environment` 这个头上真正传的那个值，不是内部主键）、带上**所有存在的环境**（哪怕它一条路由都没有，前门才好给它一个自动地址）、带一个整张表的版本号（拉的人不用逐行比对就知道有没有变）。这条路径的名字只在 `deis-wire` 里写了一次，两边都引它——之前两个互不依赖的 crate 各抄一份字面量，节点注册就因为这个悄悄坏过一次。
- deis-proxy 用**轮询**而不是推送：默认 5 秒一次，认的是它和控制面本来就共用的那把节点凭据。选轮询的理由是自愈——不管出了什么岔子（连接断了、控制面重启了、某次校验没过），下一次拉取就修好了；推送这条路最后都得再配一个周期性全量对齐才敢信，那对齐就是机制本身，推送只是优化。
- **控制面不可达的时候，最后一次收下的表继续生效，没有期限。** 拉失败只写 error、说清现在用的是哪张表、多久之前的，然后下一次接着试。数据面因为控制面连不上就开始拒绝流量，等于把一次管理面故障变成一次用户可见的故障，而控制面恰恰是最常被重启升级的那个进程。只有一种情况不同：从来没拉成功过的 proxy 手里没有表可留，它会退回到本机配置里的应用列表，也就是这个模块存在之前的行为。
- **要么整张要么不要。** 半张路由表会把线上请求发给错的应用，比一张旧表更糟。所以拉回来的那份文档是整份解析、整份校验、整份编译，最后靠一次指针交换换上去：一个请求要么看到换之前那张，要么看到换之后那张，没有看到一半的时刻。有一条不合法就整份拒绝，不做「跳过那一条」。
- 匹配顺序是：精确域名 → 通配域名（后缀越长越先，所以 `*.eu.example.com` 胜过 `*.example.com`）→ 自动预览地址 → 不写域名的路由（目录里的意思是「任意域名」，所以最不具体）。同一个域名内先比优先级、再比前缀长度，于是 `/api/v2` 胜过 `/api` 胜过 `/`，运维还能用 `priority` 手动翻盘。
- 自动预览地址：运维在 proxy 的配置里写 `routing.preview_zone`，每个环境就有了 `<环境>--<应用>.<域>` 这个地址，默认环境另外还有一个不带前缀的 `<应用>.<域>`。**分隔符是一个 DNS 标签里的 `--` 而不是点**，这是为了证书：一张通配证书只覆盖一层标签，`*.<域>` 能盖住 `pr-42--shop.<域>`，盖不住 `pr-42.shop.<域>`——后者要求每建一个应用就签一张 `*.shop.<域>`。不写 `preview_zone` 就整个关掉，一个地址也不凭空造。

**仍然要人手做的**：那条通配 DNS 记录和那张通配证书。证书自动签发是 4.12，还没做。

### 4.9 没有 Node.js 兼容

**现象**：`node:` 内建模块和大部分 npm 包用不了。

**后果**：这一条要不要修取决于定位。Edge Canon 是照着 Web 标准面写的，坚持这一点是有道理的。但现实是很多库仍然要 `node:buffer` / `node:crypto`。

**大致代价**：大，且是产品决策不是工程决策。列在这里是为了让它成为一个明确的选择，而不是一个默认。

### 4.10 没有数据面 CLI —— 已关闭

**当时的现象**：`deis` 只有 `deploy` / `versions` / `rollback` / `status` / `secret` / `logs` / `tail` / `config`。想看一眼某个应用的 KV 里存了什么、想跑一条 SQL 修数据，只能直接去戳 gRPC，而 gRPC 还要带能力令牌。

**做了什么**（`38fbeda` 加了子命令，`1be047c` 补上了它们要的那个端点）：

- `deis kv get / put / delete / list`、`deis db query / execute`、`deis blob get / put / delete`。值可以从文件进、也可以写到文件里去，所以二进制内容不用经过 shell。
- 令牌不是人去铸的。控制面新开了 `GET /api/apps/<应用>/environments/<环境>/storage-token`，凭的是部署时用的那把 API key，答的是三样东西：这个令牌授权的租户名（`<应用>.<环境>`，也就是每次存储调用要回填在 `x-deis-tenant` 上的值）、deis-store 的地址、令牌本身。三样里少一样这个答案就没法用，所以缺任何一样都是拒绝而不是留空。控制面没配 deis-store 时答 409 并说清要去配哪个字段。
- 这一条是 `38fbeda` 里那半件没接上的事：子命令写好了，它们要调的那个端点控制面还没提供，所以第一版是「命令存在、一调就失败」。`1be047c` 补上了端点。

**没做的**：`deis blob` 没有 `list`，因为服务端的 `BlobStore` 就只有 `Put` / `Get` / `Delete`（见 4.3）。`deis db` 只有 `query` 和 `execute`，`batch` 与交互式事务只在应用里能用，命令行上没有。

### 4.11 只有墙钟上限，没有 CPU 时间上限 —— 已关闭

**当时的现象**：`ExecutionLimits` 只有墙钟和 op 速率。一个 handler 等一个慢上游 25 秒，和一个 handler 死算 25 秒，在限额上是一回事——但对节点的代价差了几个数量级：前者是一条停着的线程，后者是一个租户占着一颗核，这个节点上别的应用都排在后面。

**做了什么**（`38fbeda`）：

- `cpu_time_limit_ms` 和墙钟上限并排，默认 5 秒，由同一条看守线程执行，武装的粒度也一样——一次请求、一段 `waitUntil` 尾巴、一批队列消息、一次 cron、一条 WebSocket 消息，各算一段。
- 读的是被看守那条线程自己的 `/proc/<进程>/task/<线程>/stat`，用户时间加系统时间。**为什么不用更精细的 `clock_gettime`**：`CLOCK_THREAD_CPUTIME_ID` 只认调用它的那条线程，而看守线程恰恰不是被测的那条，所以得配 `pthread_getcpuclockid`；这个 crate 不依赖 `libc`，手写 `pthread_t` / `clockid_t` / `timespec` 三个类型声明在 `time_t` 宽度不一样的目标上是一类静默错读的隐患，而一条按错读的时钟执行的限额比一条粗糙的更坏。
- 代价是分辨率：`/proc` 里的数按调度时钟滴答计，实际上都是每秒 100 次，所以读数是 10 毫秒一跳。这也是为什么配置里的下限是 100 毫秒——量化误差最多占最小可配值的十分之一。
- 把 CPU 上限设得不比墙钟上限小，等于没设：一条线程烧掉的 CPU 时间不可能多过它占用的墙钟时间，墙钟那道闸永远先响。节点启动时按应用说出这件事，不留给人去撞。

**只在 Linux 上成立**：没有 `/proc/thread-self` 的地方（macOS、Windows、`/proc` 被藏起来的容器、3.17 以前的 Linux）读不到这条时钟。这种情况下启动时会以 **error** 级别说一声，点名哪条限额没在执行、还剩下哪条在执行——一条悄悄不生效的限额比一条从没提供过的更坏。

### 4.12 没有自动证书

**现象**：证书是运维手动放置、手动续期的文件（`TLS_SETUP.md`）。

**后果**：每加一个新域名都要人工介入，而且续期忘了就是线上事故。ACME 客户端恰恰是**自建才需要**的东西——CF 用户从来不用想这件事。

**大致代价**：中。接一个现成的 ACME 库，加上 HTTP-01 挑战要走 proxy 那一跳。

### 4.13 控制面与存储没有高可用

**现象**：控制面一个 SQLite 文件，存储一个 SQLite 文件，没有复制、没有故障转移。

**后果**：快照 / 恢复解决的是**备份**问题，不是**可用性**问题。存储进程挂了，所有应用的 `ctx.services.*` 全部不可用。

这一条也**不是关于地理规模的**：同机架三台机器就够，而现在不支持。

**大致代价**：大。

### 4.14 剩下那几个 ⚠️，都不够单开一条

第 2 节里还有四行是「有一半」，每一行缺的都只是一小块，凑在这里说，免得读的人在
4.1–4.13 里找不到它们而以为漏了：

- **队列只能一条一条发**。服务端有 `rpc SendBatch`，JS 侧没接。一次投一百条要发一百
  次调用，每次都算一次 op。补法是加一个 op 和一段 JS，没有设计问题。
- **Cache API 只有 `caches.default`**，没有 `caches.open(name)`，而且它存在 isolate
  自己的内存里——换版本即失效，跨节点不共享。真要有一个跨节点的共享缓存，那是另一件
  事（一个新的存储服务），不是给这个补一个名字参数。
- **预览地址是每个环境一个，不是每个版本一个**。地址指向环境，环境指向当前那一版。
  要做到「每一版一个地址」，得让路由能指向一个版本号而不是一个环境，这会动到目录的
  数据模型。
- **控制台只覆盖机队运维**：仪表盘、节点、控制通道、命令、事件、节点配置。目录那一
  半——应用、版本、环境、部署、密钥、路由——一页都没有。REST 全都有，`deis` 也全都
  能做，所以这是「点不到」，不是「做不到」。

## 5. Deislet 比 Cloudflare 强，或更适合自建的地方

### 5.1 出站流量由运维说了算，且默认拒绝

`fetch_policy.rs` 默认拒绝环回、RFC1918 私有地址、链路本地（包括云元数据地址 `169.254.169.254`）、唯一本地与链路本地 IPv6、组播、广播和保留段。判定的是**解析之后的地址**，不是主机名。DNS 重绑定被两层堵死：IP 字面量根本不碰解析器，域名走 `PolicyResolver`，它只返回策略已经接受的地址。每一次重定向跳转都重新过同一套规则。

Cloudflare 不给运维任何对应的旋钮——Worker 能访问什么，你说了不算。对一个**部署在自己内网里**的平台来说，这个区别是决定性的：没有这层，一个应用就是内网里的一个跳板。

### 5.2 真正的交互式 SQL 事务

Cloudflare 的 D1 只有 `batch()`（一批语句原子执行），做不到「读一行、根据结果决定、再写」——因为它是分布式的。我们是一台机器上一个租户一个 SQLite 文件，所以能做，评审那一轮做了：`BEGIN IMMEDIATE` 钉住一条连接，句柄归开它的租户所有，服务端硬超时到点回滚放连接（防止 handler 拿着事务去等一个慢上游，把这个租户唯一的写者一直占着）。

这是少数几个「自建反而可以做得更好」的地方之一。

### 5.3 每一个开 socket 的地方都过同一个判定点，而且是强制的，不是文档约定

deno_core 会把 op 表挂在 `globalThis.Deno.core` **和** `globalThis.__bootstrap.core` 两个地方。两个都删了，而且有测试同时敲这两扇门，断言 `op_net_connect_tcp` 够不着。评审那一轮新加的出站 `WebSocket` 也是自己写的 op，走同一个策略，而不是直接绑 `deno_websocket` 的客户端——因为那个客户端用自己的连接器，永远到不了 `fetch_policy`。

### 5.4 真 V8 inspector 接进生产 isolate

`_inspect:<app>` 路由到一个受令牌保护的 WebSocket，把 Chrome DevTools 直接桥进正在跑的 isolate。Cloudflare 给你 `wrangler dev` 里的 devtools；在生产 isolate 上单步调试，它不提供。

### 5.5 SQL 沙箱是靠 SQLite 自己的授权器守的

评审那一轮修的那个严重漏洞（见 6.2）的修法值得单独说：不是靠检查 SQL 文本关键字——那种检查一个前置注释就能绕过——而是装 SQLite 的授权器回调（authorizer），它在解析器**下面**，绕不过去。PRAGMA 用白名单而不是黑名单，因为黑名单会随版本变旧。

升级到 rusqlite 0.40 时又补了一处：这个库开始会报告「授权器没装上」这件事——以前它只能悄悄发生。deis-store 原来丢掉这个返回值，现在改成让这条连接直接失败。理由是：装不上还把连接发出去，等于发出一条看起来有防护、实际什么都不挡的连接，授权器本该拒绝的每一条语句——ATTACH 到别的租户的文件、`VACUUM INTO` 到任意路径、白名单之外的 PRAGMA——都会照跑不误。

### 5.6 节点不替应用继承自己的 `HTTP_PROXY`

`egress_proxy.rs`：这些变量在主线程读一次就从进程环境里删掉，免得 `deno_fetch` 悄悄把应用流量绕过去，然后显式交还给节点自己的三个客户端。这是托管平台永远不用想、自建运维必须想的一类意外。

### 5.7 一份源码编译到四个目标

`deis-build` 能把同一个项目产出 Cloudflare Workers、Deno Deploy、腾讯 EdgeOne 或本平台的可部署物，而且目标缺少某个已声明特性时**在构建期就拒绝**。Deislet 既是目的地也是一扇出门——Cloudflare 没有兴趣当后者。

### 5.8 数据是你的，且可检视

一租户一个 SQLite 文件、对象在本地磁盘、日志在你自己的 telemetry 进程、Prometheus 指标在你自己的端点。没有按次计费表，没有出网流量费。备份是 `deis-store snapshot`，用 `VACUUM INTO` 取一致快照——`cp -r` 一个 WAL 模式的库取不到，而且不会报错，只是恢复出来是错的。

## 6. 修过什么

分两段：评审过程中做的（6.1–6.3 加「其余」），和评审写完之后那四个提交做的（最后一节）。

### 6.1 平台声称的执行超时，对同步死循环完全不生效

每个 isolate 跑在自己的 OS 线程上，配一个 `current_thread` 的 tokio runtime。六条执行路径里有五条用 `tokio::spawn` 一个定时器来做超时。问题是：**那个定时器要等这条线程回来轮询才能跑**。

所以 `export default function handler() { while (true) {} }` 配 300 毫秒的预算，实测跑了 **75 秒还在跑**，一个核跑满，那条运行时线程永久失联。而任何一个用 `await` 空转来测超时的测试，从头到尾都是绿的。代码里甚至把这个洞写成了「超时机制的既有特性」而不是缺陷。

修法是把所有预算都改成一条**属于该 isolate 的 OS 线程**（V8 允许从任何线程 terminate）。修的过程中还踩到第二层：第一版仍然不生效，因为看门狗是在 `execute_script` **返回之后**才武装的——而 handler 的第一段同步代码就跑在 `execute_script` 里面，死循环根本没让它返回。改成先武装再执行之后，同样的死循环 0.43 秒被切断，同一个 isolate 随后继续正常服务。

### 6.2 一个租户能读写其他所有租户的数据库

`database.rs` 开头写着「文件级隔离是这里最省事的正确答案：一个租户没法指名另一个租户的表」。每一个分句都是假的。普通应用代码通过 `ctx.services.database` 做到了：

```js
const list  = await db.query("PRAGMA database_list");   // 得知自己的文件路径
const other = list[0].file.replace("attacker.production", "victim.production");
await db.execute(`ATTACH DATABASE '${other}' AS victim`);
await db.query("SELECT * FROM victim.secrets");         // 读到了别人的数据
await db.execute("INSERT INTO victim.secrets ...");     // 也写进去了
```

另外 `VACUUM INTO '/任意路径'` 能在存储进程能写的任何地方创建文件。

修法见 5.5。

### 6.3 内存上限从来没有被设置过

`IsolateSpec.memory_limit_mb` 会变成 V8 的 `heap_limits`，还挂了接近上限时终止执行的回调——这套机制是对的，而且**从来没有被喂过值**：它来自 `config.limits.as_ref().map(|l| l.memory_mb)`，而控制面和 bundle manifest 里没有任何一处填过 `ResourceLimits`。所以 `limits` 恒为 `None`，每个 isolate 都跑在 V8 的默认堆上。一个应用无限分配，撑爆的是整个节点进程，同进程里其他应用一起死。

超时和 op 速率都有平台级默认值可以被应用收窄，唯独内存没有默认值，于是形同虚设。现在有了。

### 其余

二进制体端到端（此前 `return fetch(<图片>)` 会损坏内容）、KV 值改字节并补齐 `list()`、SQL `batch()` 接进 JS、队列消息体改字节、存储调用带每租户能力令牌（非环回绑定且未配密钥时**拒绝启动**，而不是放行）、定时快照与保留策略、`waitUntil` 尾巴和 WebSocket 消息的执行预算、请求体上限（proxy 和节点两处）、出站 `WebSocket`、十个全局补齐、Cache API 不再破坏二进制、平台全局不能被改写并泄漏到同一 isolate 的下一个请求、入站帧类型不再由载荷自己声明。

以及一件方法上的事：写代码的一方和攻击的一方是分开的，不让人给自己判分。三轮下来对抗方一共打出 12 条，其中 1 条最高危、4 条高危——**没有一条是单元测试能发现的**，全部需要真的部署一个应用去打。

### 评审之后：四个提交

**`38fbeda`** 一次做了五条缺口的主体：静态站点的三个规则（4.4）、控制面路由接到前门（4.8）、数据面 CLI（4.10）、按次调用的轨迹与延迟直方图（4.6）、CPU 时间上限（4.11）。其中四条当时就完整了，第五条只做了一半，而**提交说明把这半件事直接写了出来**，没留给后来的人去发现。

**`1be047c`** 补的就是那一类：六个「写好了、测过了、注册过了，但没有任何一条请求走得到」的功能。找法是从上一波每一个新符号往外走，看有没有调用者——这条检查从此成了「关掉一条缺口」的收尾动作。六个分别是：

1. 静态站点的规则在装载时编译好了，可只有测试在调 `AssetBundle::serve`，HTTP 入口还在做一次朴素的索引查找。现在它按规则服务了，带路径也带查询串，`GET` 和 `HEAD` 都走。
2. `env.ASSETS.fetch()` 只有 Rust 那一半，没有 op、没有绑定。两样都补上了，并且 `ASSETS` 成了保留键，部署里同名的变量顶不掉它。
3. `deis_runtime_memory_cutoffs_total` 这个计数器从来没有人加过，于是运维从它读到的是「从来没有 isolate 撑爆过堆」——一个从没被写过的计数器和一个真的是零的计数器长得一模一样。现在接近上限那个回调会记它。
4. 清单里的 `limits` 块走到了消息里就停住了，节点建 `AppConfig` 时写的是 `limits: None`。现在会解出来并生效，而且每一个字段都对着节点自己的天花板夹一次——应用只能要求被管得更严，永远不能更松。
5. 轨迹有生产者、有存储、有查询接口，没有读的人。`deis trace` 是读它的那一头。
6. `deis kv/db/blob` 要调的那个存储令牌端点控制面没提供。现在提供了，认的是部署用的那把 API key。

这六条里有两条当时只走通了一半，是给演示加验证的时候撞出来的：

- 第 4 条。清单里的 `limits` 块从控制面到节点这一段是通的，可**没有任何构建器往清单里写过这个块**——`.config.json` 里的 `limits` 解析完就没人读，字段名（`timeout` / `maxPayloadSize` / `maxConcurrency`）和平台认识的那几个也对不上。于是真部署出来的应用仍然是 `limits: None`，6.3 那句「现在有了」在那时还只对了一半。现在项目里的 `limits` 会被译成清单里的同名块，块的定义搬到了 `deis-bundle`（构建写它、控制面校它、节点执行它，三方共用一份，而不是各写一份等着走样）。
- 第 5 条。轨迹有人读了，可节点记的时候用的是不带任何事实的那条重载，于是每一行的目标、方法和状态码都是空的——`deis trace` 甚至为此专门印一句「这些行既没有目标也没有状态，那是节点上的缺口，不是空结果」。现在请求路径把方法、URL、状态码和失败原因一并记进去，`deis trace` 的一行说得出「哪个请求、答了什么、怎么结束的」。

两条都由 `scripts/demo.sh verify` 盯着：上限那三项是照真请求和节点自己的日志判的，轨迹那一项开着流再发请求，跟到的必须是这一次调用。

**`b149c42`** 把前门从 pingora 0.5 升到 0.8.1。0.5 带着两个请求走私漏洞（CVSS 9.3），在一个多租户的边缘上，请求走私意味着一个租户的请求被交给另一个租户的应用，所以这是安全下限而不是偏好。**顺带堵上了我们自己的一个洞**：请求体上限原来对任何带 `Upgrade` 头的请求一律放行，而 pingora 0.5 只能从请求头判断这件事——于是一个普通的分块上传只要自称是升级，就能不受限地送到节点。0.8 能看到节点到底有没有回 101，现在问的是这个，两半都有对着真二进制跑的测试。

**`3753cb2`** 离开了 deno 的私有分支，改用发布版的 `deno_runtime` 0.266。那个分支存在的理由只有一条提交那么大，而它把运行时按在 31 个小版本之前，连带 hyper 0.14、rustls-webpki 0.102 和 aws-lc-sys 0.29 一起，中间夹着九条公告。`cargo audit` 这一次从 13 条降到 4 条（连同前两轮，是从 17 条降到 4 条），剩下的四条连同各自的理由写在 `.cargo/audit.toml` 里：三条是「链接进来了但应用够不到」，第四条（RSA 的 Marvin 计时侧信道，上游还没有修复版）应用够得到，那条写清了什么样的用法会暴露、暂时该改用什么。这次升级里和本文结论有关的两点：deno_fetch 现在会拿「名字解析出来的地址」再对一次拒绝名单，而拒绝名单写不出「例外」，所以运维用域名开的白名单会被这道兜底否掉——现在白名单里出现域名时就不装那份地址段兜底，机制仍然是策略本身（它在每个地址、每一跳上都认白名单）；另外 rusqlite 0.40 开始会报告「授权器没装上」，deis-store 从丢弃这个结果改成让这条连接直接失败——那个授权器就是租户的 SQL 沙箱（见 5.5），装不上还把连接发出去，等于发一条看起来有防护、实际没有的连接。
