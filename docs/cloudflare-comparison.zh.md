# 功能性评审：Deislet 对照 Cloudflare Workers / Pages

日期：2026-08-31。对照的代码是 `3753cb2`。

这份评审第一次写出来时对照的是 `fea1ab8`。之后四个提交改动了它的结论，全文按新代码逐条重核过：
`38fbeda`（静态站点规则、目录路由、数据面 CLI、调用轨迹、CPU 上限）、`1be047c`（把六个「写好了但没有调用点」的功能接到真实请求路径上）、`b149c42`（前门升到 pingora 0.8.1）、`3753cb2`（离开 deno 分支，改用发布版 deno_runtime 0.266）。第 6 节末尾列了这四个提交各自关掉了什么。

## 0. 这份评审的口径

Deislet 的定位是**私有化部署的小平台**：一个机房、几台机器，没有全球任播网络，没有几百个边缘节点。所以「我们节点少」不算差距——那是定位本身。这份评审只问一件事：

> 一个开发者按 Cloudflare Workers 的写法写好的应用，搬到 Deislet 上，**哪些地方会写不出来、跑不对、或者运维接不住**？

判定分三档：

- ✅ 有，且经代码核实
- ⚠️ 有一半，缺的部分写明
- ❌ 没有

每一条 Deislet 侧的判定都对着代码核过，不是按文档。这一点必须强调，因为这个仓库反复出现过「文档声称的能力代码里没有」——最初那一轮就修了十几处，之后又出现过反过来的一种：功能写好了、测试也有，但**没有任何一条真实请求能走到它**（`1be047c` 一次性接上了六个这样的功能）。所以判 ✅ 的门槛是「从外面打一发请求能用到」，不是「代码里有这个函数」。

---

## 1. 结论

第 2 节那八张表一共 77 行：**✅ 57、⚠️ 4、❌ 16。**

16 个「没有」里，绝大多数分成两堆：一堆是 **Cloudflare 在卖它自己的机器**（Workers AI、Vectorize、Hyperdrive 之类），自建装机缺的是硬件不是平台功能；另一堆是**多接入点网络才有的属性**（第 3 节列了 11 项）。剩下**3 项是自建用户真会撞上的**，第 4 节逐条展开——那一节里另有 10 条已经关掉了，编号留在原位，写清做了什么；第 4 节末尾还收了四条「有一半」的，每条缺的都太小，不够单开一条。

按撞上的概率和痛感排，还剩下的是：

1. **没有 Durable Objects 或任何协调原语** —— 单实例执行、房间、在线名册，一个都做不了（4.2）
2. **一种资源只能挂一个具名绑定** —— 一个应用绑不了两个数据库、两个桶（4.5 的前一半）
3. **控制面与存储没有高可用** —— 都是单进程单文件（4.13）

Node.js 兼容（4.9）另算：它是要先拍板的产品问题，不是排期问题。

需要说明的是：这个清单是**几轮修完之后**的清单，比第一稿短了不少。第一稿的前五名里有三条（`waitUntil` 不受限、没有事务、请求体没有上限）在评审那一轮就修掉了，还顺带修掉了一个跨租户读写数据库的严重漏洞；随后又关掉了十条——静态站点规则、控制面路由接到前门、数据面 CLI、按次调用的轨迹与延迟分位数、CPU 时间上限、对象存储的列举与范围读与条件写、自动签发续期证书、流式响应过边界、compatibility date 与具名开关，以及账号 / 角色 / 作用域 token / 审计日志。第 6 节列了这几批各自做了什么。

## 3. 因为是单集群，所以本来就不需要的

这 11 项不是差距，列出来是为了避免后来者把它们误当成待办：

- **灰度百分比放量**。CF 需要它是因为一次变更同时落到几百个机房，得有统计意义的爬坡。这里部署只到少数几台机器，回滚是挪指针、一秒完成，「蓝绿 + 秒级回滚」在这个规模上覆盖了同样的需求。（如果机队真长到几十台，按节点分批仍然值得做；按百分比那套机器不值得。）
- **Smart Placement / 区域放置提示**。只有一个地方能跑，没什么可决定的。
- **任播、全局负载均衡、地理调度、Argo**。都是多接入点网络的属性。
- **Tiered Cache / Cache Reserve**。它们存在是为了减少跨机房回源。这里源站就在旁边。
- **Durable Object 的司法辖区与位置提示**。运维已经选好机器在哪了。
- **Workers for Platforms / dispatch namespace**。那是「大规模托管别人的不可信 Worker 并计费」的产品。自建装机真正需要的那部分是 RBAC，已经做了，见 4.5。
- **免费版 / 付费版的限额分层与账号级日配额**。没有计费套餐要区分。
- **多区域存储复制与只读副本**（D1 read replication、R2 jurisdictions）。单集群没有意义；单集群内为了可用性做复制是另一回事，已单列为真实缺口。
- **Workers AI 与 Vectorize 作为一等绑定**。这两个是 CF 在卖自己的 GPU 机队和索引服务。自建用户通过 `fetch` 调外部推理 API 今天就能用，而且我们的出站策略让这个调用是受管控的。缺的是硬件，不是平台功能。
- **Hyperdrive 的全球连接池层**。它的价值是在每个机房旁边握着热连接，免得悉尼的 Worker 现开一条到弗吉尼亚的 Postgres 会话。单集群里数据库就在同一个局域网。

## 4. 真正要紧的缺口

按「自建用户撞上的概率 × 撞上之后有多难受」排序。每条给出：现象、后果、今天只能怎么办、大致代价。

编号保持不变，**已经关掉的五条也留在原位**，写清做了什么——因为第 7 节的排序是按这些编号说话的，一条缺口悄悄消失，读排序的人会以为自己漏看了。

### 4.1 流式响应过不了 isolate 边界 —— 已关闭

**当时的现象**：`ReadableStream` / `WritableStream` / `TransformStream` 三个构造器都在，handler 内部用它们完全正常。但响应体在跨 Rust↔JS 边界时是一整块完整的字节数组（`isolate.rs` 的 `PendingResponseBody`），handler 必须先把整个响应体凑齐才能返回。

**当时的后果**三条：Server-Sent Events 写不出来——SSE 的响应体按定义永不结束，于是 handler 永不返回，撞到执行上限，客户端什么也拿不到；代理大文件会整个进内存，撞的是这个应用自己那 128MB 的堆；首字节时间等于整个 handler 的耗时，哪怕第一个字节早就准备好了。最阴的是：三个构造器都在，照着流写的代码能编译、能跑、行为却是错的——它不报错，只是不流。

**做了什么**：

- **回答的形状从「一块字节」改成三选一**。`ResponseBody` 是「没有 body」「一整块字节」「一条还在生产的流」。前两种就是从前那个 `Option<Vec<u8>>` 的两半，走的路一步没变，绝大多数响应仍然走它。判定规则只有一句：**应用交给 `Response` 的 body 是不是一个 `ReadableStream`**。字符串、buffer、Blob、`null` 一律照旧整块出去；`new Response(stream)` 走流；`fetch()` 自己答回来的那个 `Response`（这个运行时没有造过它）也走流——`return fetch(url)` 是所有人写的第一个反向代理，从前它会把上游整个读进这个 isolate 的堆里。
- **背压就是一个 op 的 await**。`op_deis_stream_write` 是异步 op，节点这边的队列只放 2 个 chunk，队列满了它就不 resolve。客户端读得慢，生产者就停在自己的 `await` 上：不占 CPU，也不会有第三个 chunk 被塞进节点的内存。上限在这里，没有从 isolate 搬到节点。chunk 多大是应用自己的事，而它本来就受那个应用的堆上限管，所以这里多出来的最多是两份。
- **流不占住 isolate**。一个 (应用, 环境) 是一条线程上的一个 isolate，请求是排着队进去的；一条一直占着它到客户端读完的流，会让一个读得慢的人挡住这个应用的所有请求。所以流是**在请求之间被推进**的：`runtime/pool.rs` 的消息循环用 `select!` 一边等新消息、一边推流，新请求一到就把推流那一半放下、先答请求，答完再回来接着推。代价是另一个请求最多多等「生产一个 chunk」的时间，而不是等整条流。
- **预算是它自己的一个数**。`stream_timeout_ms` 默认 5 分钟，和请求的 30 秒差一个数量级，因为两者量的不是一回事：请求的上限是「调用方等答案等多久」，而流已经答过了。到点是**节点关流**，不是终止 isolate——终止会把同一个应用的其它流和其它请求一起打死。客户端看到的是一次半路失败的传输（200 早就发出去了，没有状态码可以改），节点在 warn 里写清是哪一条流、送了多少字节、上限是多少、要调哪个键。CPU 那一半仍旧归看守线程：一个不肯让出控制权的生产者只能靠终止 isolate 停下来，它在日志里的名字是 `Watched::ResponseStream`。
- **取消会传下去**。客户端挂断 → 节点这边的接收端被丢弃 → 生产者的下一次写立刻失败 → `js/runtime.js` 调 `reader.cancel()`，应用写的 `cancel()` 回调会跑。节点也主动发现：推流的那一半同时在等「有没有哪条流的客户端走了」，走了就叫停生产者，而不是让它对着没人读的队列一直写到预算耗尽。
- **一次调用里开出去的东西，归这条流管**。handler 里那个 `fetch` 往往就是喂这条流的源，而「出站调用活得和请求一样长」是这个运行时别处都成立的规矩——照旧的话它会在 handler 返回时被清扫掉。现在流会把 handler 还开着的出站调用和 interval **接管过去**，并按流自己的时钟重新上闹钟，流结束时一起清掉。`js/bootstrap.js` 里那一节写了为什么不能干脆留在共享的集合里不动：留着的话，清掉它的会是**下一个请求**，故障就取决于别人的流量了。
- **前门不能把它攒起来**。deis-proxy 现在对「节点没有报长度」的响应关掉压缩。pingora 的压缩器不是每个 chunk 都 flush 的：一个 40 字节的 SSE 帧交给 gzip，出来是空的，客户端就在那儿等前门手里攒着的字节——那正是这条缺口本身，只是从 isolate 挪到了前门。代价是这类响应最后一跳不压缩，而所有知道长度的响应（也就是绝大多数，包括每一个大的静态文件）照压不误。

**跟着来的一条要知道**：一个 chunk 就是一次 op 派发，所以 `rate_limit_ops_per_sec`（默认 1000）同时是「一秒能写多少个 chunk」的上限。写很小的 chunk 的生产者会先撞上它，而不是撞上任何字节速率。撞上时限流器是从 op 派发内部终止 isolate 的，冒出来的话既没有应用名也没有上限值，所以节点把它翻译成一句说清了 ops/sec 和该怎么办的话，再照失败结束每一条流。

**怎么验的**：`scripts/demo.sh verify` 里七条检查，六条穿过 deis-proxy：SSE 的五帧是分五次到的（头 13ms 到，末帧 621ms 到，handler 每帧之间停 150ms）；响应是 chunked、没有 `Content-Length`、即使请求带了 `Accept-Encoding: gzip` 也没有 `Content-Encoding`；`new Response(upstream.body)` 转发一个慢上游，六段是照上游的节奏到的；生产者半路抛异常，客户端拿到 200 和两帧，然后是一次没有结束块的传输；客户端读两帧就挂断，应用的 `cancel()` 跑了，帧计数器随后两次请求都不动；一条流开着的时候另一个请求照常在 19ms 内答完并带着 `Content-Length`；以及一条永不结束的流被节点按 4 秒的上限关掉。

**没做的**：请求体仍然是整块的。`PendingRequestBody` 没动，handler 拿到的 `Request` 还是一个可以 `arrayBuffer()` 的完整 body，节点的 `max_request_body_bytes` 还是那个上限。上传方向要流式是另一件事——要动 dispatcher 的读取、要有一个反方向的 op、`request.body` 要变成真的可读流——这一轮没做。`stream_timeout_ms` 也还没有 per-app 的收窄口，和 `wait_until_timeout_ms` 一样是运维的数。另外，一条流的生产者不能跨 chunk 持有一个出站 WebSocket：socket 的生命周期本来就是「一次调用」，而推流是另一次调用，应用会拿到一句说清了那个 socket 去向的错误，而不是静悄悄地坏掉。

### 4.2 没有 Durable Objects，也没有任何协调原语

**现象**：没有任何东西能保证「同一个键的操作被串行地、在同一个地方执行」。

**后果**：一整类东西做不了——串行计数器、分布式锁、每实体状态机、多人协作 / 房间、跨连接的 WebSocket 在线名册。

这一条**不是单集群的后果，恰恰相反**：单集群是最容易做单实例 actor 的地方，不需要任何全局路由。

**今天只能怎么办**：两条路。一是交互式事务，覆盖同一个 SQLite 文件里的「读—判断—写」；二是对象存储的条件写（4.3），`put(key, body, { onlyIf: { ifNoneMatch: "*" } })` 是一个真正的、跨进程跨节点的原子占位，可以拿来做锁和乐观并发，输的一方会被明确告知它输了。剩下的——每实体的单线程执行、房间、在线名册——还是没有替代。

**大致代价**：大。要有对象标识到节点的路由、每对象的单线程执行、每对象的持久状态，以及一个应用调用另一个对象的调用路径。

### 4.3 对象存储只有 put / get / delete —— 已关闭

**当时的现象**：`blob.proto` 就三个方法，`GetRequest` 只带一个 key。

**当时的后果**：不能翻页列举一个桶——存用户上传的应用只好自己在 KV 或 SQL 里另记一份索引，写到一半失败一次，两边就对不上了；不能只问一个对象有多大或者是什么类型，得把整个对象拉下来再扔掉；不能按字节范围取，所以视频拖进度条、大文件断点续传都不行，而节点上每个 isolate 有内存上限，「整个」有时候根本取不下来；不能做条件写，两个请求同时对同一个键做「读—改—写」，其中一个的写会悄无声息地消失，而这个平台别处也没有任何可以拿来做 compare-and-set 的东西。

**做了什么**：

- 服务端加了 `Head` 和 `List` 两个方法，`Get` 多了一个可选的 `range`，`Put` 的头和 `Delete` 多了一个可选的 `precondition`。四件事都一路接到了应用手里：proto → deis-store 的存储层 → deis-runtime 的客户端 → op → `ctx.services.blob` 的 JS 绑定 → `deis blob` 命令行。每一层都有真正的调用方，`scripts/demo.sh verify` 里六条检查分别从应用和命令行两头验。
- **版本标识用的是内容摘要**，也就是对象的 sha256，而不是另起一个代数号。理由是这个值本来就在：上传时算过、元数据行里存着、每次读都随流带回来、客户端还拿它验过一遍完整性；应用把对象转成 HTTP 响应时也正好要往 `ETag` 里填一个值，填这个还能被对方验证。代价要说清楚：它比较的是「对象里还是我读到的那份内容吗」，不是「这中间有没有人写过」。如果第二个人写了别的内容、第三个人又把原内容写了回来，条件写照样会成功——而对「读—改—写」来说这样成功是对的，因为要写下去的东西本来就是照当前内容算出来的。要数写入次数的场景需要一个计数器，这不是计数器。
- 条件不成立**不是错误，是另一种结果**。响应里有一个专门的 `precondition_failed` 字段，JS 里 `put` 返回 `null`、`delete` 返回 `false`，命令行退出码是 3。理由是：这一种失败恰恰是应该重试的（重新读一遍对象再来），而其余每一种失败都不该重试；如果只给一句错误话术，调用方就只能去匹配错误文本，文案一改它就开始重试错误的东西了。
- 判断和写入在**同一个 `IMMEDIATE` 事务**里完成：先读当前摘要，再按条件决定写不写，这一行在中间一直被写锁按着。所以两个人同时说「只有这个键不存在时才写」，只可能有一个被告知写成功。测试就是两个任务抢同一个键，断言恰好一胜一负，并且输的那个必须拿到赢家留下的 etag——不然它没法重新对着那个值再来一次。
- **范围读照 HTTP 的说法办**：`bytes=<起>-<止>`、`bytes=<起>-`、`bytes=-<末尾若干字节>` 三种都支持。末尾超出对象的会截到对象结尾，这是每个 HTTP 客户端表达「头一兆，不够就全给」的方式；而起点落在对象结尾之后的，会以一个**单独的状态码** `OUT_OF_RANGE` 返回——应用要靠它区分「这个对象没有这段字节」（答 416）和「根本没有这个对象」（答 404）。范围在服务端解析一次，答复里带回真正给出的偏移和长度，应用照着拼 `Content-Range` 就行，两层不会各算一遍再算出两个数。
- 范围读**也验完整性**。整个对象的读是拿 `BlobInfo.sha256` 校的，切片当然对不上它，所以服务端一边发一边把这一段的摘要算出来，放在流的最后一条消息里，客户端拿它校验。不这么做的话，范围读就会成为这个平台上唯一一条「交给应用的字节没有任何人检查过」的路径。
- **列举是分页的，而且上限不在调用方手里**：一页默认 200 条、最多 1000 条，要得更多只会拿到 1000 条加一个游标，而不是一个错误。带 `delimiter` 时按 S3 的做法把一层折成「文件夹」，并且**折完一个文件夹就直接跳到它后面**接着扫——所以列一个百万对象的桶的顶层，代价是文件夹的个数，不是对象的个数。游标是不透明的：它同时记住「从哪儿继续」和「那个位置本身算不算」，调用方原样传回来，不要自己拼一个。判断有没有下一页看的是游标在不在，不是这一页短不短——正好装满的一页后面也可能什么都没有了。
- 租户边界和原来那三个方法完全一样，靠请求头 `x-deis-tenant`，proto 里没有任何字段能让调用方指定租户。列举比读更需要盯：读要报得出键名才有东西，列举是一个开放提问，扫到什么就是什么。所以专门写了一条测试，让另一个租户用四种问法试探——空前缀全列、直接点名对方的前缀、带 `delimiter` 想看对方的文件夹名、把对方扫描得到的游标原样递过来——四次都只能看到自己的东西。

**没做的**：自定义元数据（除 `content_type` 以外再挂任意键值）还没有，条目里那一行仍然是 ❌。上传方向的分段续传也没有（下载方向的续传由范围读支持了）。条件读（用 `If-None-Match` 省掉一次传输）没做，应用可以先 `head` 再自己判断。

### 4.4 静态站点缺 `_redirects` / `_headers` / SPA 兜底 —— 已关闭

**当时的现象**：三个都没有。地球上每一个静态站点生成器都会吐 `_redirects` 或 `_headers`，而这个平台是当作「自建版 Pages」宣传的；想给一个静态路径加一条重定向或者加一个 `Cache-Control`，就得写一个函数——这恰好绕开了 asset-first 的全部意义。

**做了什么**（`38fbeda` 做了解析和编译，`1be047c` 把它接到请求上）：

- 格式定义放在 `deis-bundle` 的 `site.rs` / `redirects.rs` / `headers.rs`，编译器和节点共用一份，谁都不独占这个格式。构建时解析，**规则写错就构建失败**，报出文件名、行号和那一行的原文；构建产物里不再带这两个文件本身。
- 节点在装载一版的时候把清单里的文本编译成表，之后每个请求只是查一次哈希、扫一张定长的表。
- 一个请求的判定顺序是：先看资产索引（路径命中文件就是那个文件）→ `_redirects`（按作者写的顺序，首条命中者胜）→ 清单里声明的函数路由（认领了就归 isolate）→ 兜底行为。`_redirects` 排在函数路由**之前**是有意的：作者手写的规则是他做的决定；兜底不是手写的，所以让位。
- `_redirects` 的 200 是改写（地址栏不变、返回目标的字节），404 是带 404 状态返回目标，其余状态是真跳转。跳到站外只允许「真跳转」且主机名必须是常量，改写跳站外一律拒——改写是从**本包**里取字节，允许它跳站外等于让节点按作者给的地址开一条不经出站策略的连接。
- `_headers` 是所有命中的块都生效、靠后的覆盖靠前的（和 `_redirects` 相反，因为头是叠加的、跳转是单个决定）。`! 名字` 只能去掉这些块自己设过的头；节点算出来的 `Content-Type` / `Content-Length` / `ETag` / 默认 `Cache-Control` 去不掉，`x-deis-` 开头的平台头也不许写。
- 兜底行为在项目配置里写 `assets.notFound`：`none`（交给 isolate 自己答 404）、`404-page`（返回 `404.html`，状态 404）、`single-page-app`（返回 `index.html`，状态 200）。不写而包里有 `404.html` 时按 `404-page` 处理。
- 一处刻意的收窄：通配符 `*` 只能当路径的最后一整段，`/*.jpg` 这种段内通配在构建期就拒绝，不做「半懂」。按扩展名设头请把文件放进一个目录再匹配 `/img/*`。

**没做的**：`_redirects` 里没有强制 HTTPS、没有按国家或语言分流这类 Cloudflare 后来加的条件规则。

### 4.5 一种资源只能挂一个绑定；账号体系已关闭

原来这一条把两件事凑在一起说，因为它们都属于「第二个人 / 第二个用途加进来的时候就不够用了」。账号那一半已经做完，绑定那一半还开着。

**还开着的：具名绑定**。一个 `(应用, 环境)` 只有一个 KV、一个数据库、一个对象存储、一个默认队列。冷热数据分开、一个应用挂两个桶，没有任何表达方式。（`ServiceConfig` 上的 `namespace` 和 `connectionString` 评审那一轮删掉了——两个字段都在，但全仓没有一个读者，留着是个陷阱：作者能设，没人读。）**大致代价**：中等，要动 manifest、控制面数据模型、绑定注入。

#### 账号与 RBAC —— 已关闭

**当时的现象**：`api_auth_enabled` 加一串 `api_keys` 就是全部的授权模型。每一把 key 都能部署任何应用、读写任何密钥、给任何租户签存储令牌、删任何东西；没有账号，没有角色，没有作用域，也没有任何记录说明谁做了什么。一台机器上放几个团队的应用时，这等于「拿到 key 的人都是 root」，运维上手第一件事只能是「谁都别给」——那就把平台本身否掉了。

**做了什么**：四样东西，都在控制面里，都在人这一侧的那条通道上（节点那把 `node_preshared_keys` 和存储那把 `storage_auth_secret` 一点没动，它们面对的是机器，不是人）。

- **账号**。审计行里被追责的那个名字，带一个角色：`owner`、`maintainer`、`deployer`、`viewer`。角色是**上限**而不是授予，而且每个请求都重新读一遍——把一个账号从 `owner` 降成 `viewer`，它已经发出去的每一把 token 在下一个请求就只剩「读」，不用把那些 token 一个个找出来吊销。停用一个账号是另一回事：它的 token 全部被拒但没有被吊销，重新启用就原样恢复。
- **作用域**。写成 `<动作>:<应用>/<环境>`，只有这一种形状：`deploy:myapp/preview`、`read:*/*`、`secrets:myapp/production`、`storage:myapp/production`、`admin:*/*`。`*` 只能整段代替，没有 `my*` 这种前缀匹配——一眼看得出一把 token 够得着哪里，比多一分表达力重要。动作只有五个，互相之间只有一条推导：任何动作都顺带允许「看」它作用的那个东西，别的一概不推导——`admin` 推不出 `deploy`（想发版就把 `deploy:*/*` 写下来，写下来了 `deis token list` 就看得见），`deploy` 也推不出 `storage`。判定放在一个地方：一张「方法 + 路径 → 需要什么」的表，加上挂在人这一侧路由外层的一道中间件。表里最后一条兜底要求 `admin:*/*`，所以将来有人加了路由却忘了在表里写一行，那条路由是**只有管理员能进**，不是谁都能进。
- **token**。形如 `deis_pat_<公开号>_<秘密>`，秘密是 32 字节随机数。库里只存公开号和秘密的 SHA-256，所以把整张表读走也换不到一把能用的凭证；创建的那一次是它唯一一次出现，之后连控制面自己都拿不回来。用的是普通摘要而不是 argon2 这类慢哈希，因为这里没有人选的口令可猜，猜的是 256 位真随机数——慢哈希在这里只会给每个 API 调用加一次故意的慢。吊销是改一行，认证时每次都查库，所以下一个请求就失效，没有缓存要过期。被吊销的、账号被停用的、根本不存在的，对调用方是**同一个** 401（否则拿着偷来的 token 的人就能问出它是不是已经被发现了），在控制面自己的日志里是三句不同的话。
- **审计日志**。所有会改状态的调用——部署、回滚、密钥读写、签 token、改账号、改路由——都记一行：谁、做了什么、哪个应用哪个环境、从哪个地址来、结果是什么。被拒的调用照样记，而且记得和成功的一样细，还多一句「差哪个作用域」。成功的读不记，否则这张表就变成访问日志，真正要找的那两行反而找不到；唯一例外是签存储令牌，它是「读」，但给出去的是一把凭证。控制面里没有任何地方更新或删除这张表，也没有任何接口通向那里，`owner` 也没有；要抹掉一行得直接动数据库文件，那和拿到密钥主密钥是同一级别的权限。密钥写入记的是密钥的**名字**，绝不是值——那道中间件只在两条路由上读请求体（`POST /api/apps` 和创建环境，它们把要创建的名字写在体里而不是路径里），两条都不带密钥值。

**旧的 key 怎么办**：原样继续能用，一行配置都不用改。启动时每一条 `api_keys` 在库里留下一条记录（只留 4 字节指纹；key 本身仍然只对着配置文件做定长比较，库里连它的完整摘要都没有），`deis token list` 会把它列出来、标成 `unscoped`，表尾和启动日志再报一次「还有几把无作用域的凭证」——那个数字就是运维要推到 0 的东西。从配置文件里删掉一条，下次启动那条记录就被标成已吊销，因为文件才是它们的权威。另外补了一个原来的坑：`api_auth_enabled = true` 而 `api_keys` 为空、库里也没有 token 时，以前是谁都进不来的死局，现在会铸一把 owner token 并在日志里印一次，和没配 `node_preshared_keys` 时的做法一样。

**边界最锋利的那条**：签存储令牌的接口。它给出去的是一把直接对 deis-store 说话、不经过控制面、而且不过期的凭证。所以它有自己的动作 `storage`，任何别的动作都推不出它，而且带 `storage` 的作用域**必须把应用和环境都写实**——`storage:*/*` 和 `storage:myapp/*` 在写下来的那一刻就被拒，不是等到用的时候。一把 `deploy:*/* secrets:*/*` 的凭证签不出任何租户的令牌；要签就得一个租户一个租户地写下来。无作用域的老 key 仍然签得出来，因为它按定义就是 root——它正是这套模型要运维退休掉的东西。

**CLI**：`deis account create / list / update`、`deis token create / list / revoke`、`deis audit`。`deis token create` 把秘密印一次并说清这是唯一一次；`deis token list` 把无作用域的那几行标红并报出数目；`deis audit` 能按应用、环境、账号、动作、结果、时间段筛，被拒的那几行把原因单独印在表下面。

**没做的**：`api_auth_enabled` 仍然是总开关，关着的时候人这一侧的 API 和以前一样是敞开的（升级不能把没开认证的装机打死），审计日志照记、作者记成 `anonymous`，启动时报一行 warn 说清楚。审计表没有留存期，不会自己清。控制台里没有账号和审计的页面。作用域按 `(应用, 环境)` 划，划不到更细（比如「只能改这一个密钥」）。token 也还没有有效期，只有吊销。

`scripts/demo.sh verify` 里有七条盯着它：配置文件里那把 key 被列出来并标成无作用域；一把 `deploy:demo/preview` 的 token 能把 preview 部署到它正在跑的那一版，而对 production、对自己环境的密钥、对审计日志、对凭证列表全是 403；`deploy:*/* secrets:*/*` 签不出存储令牌而 `storage:demo/production` 能签，并且 `storage:*/*` 在创建时就被拒；吊销后的下一个请求就是 401，和一把从没铸过的 token 的回答一模一样；审计里那条密钥写入记着密钥名字而不是值；被拒的调用连原因一起记着；`DELETE /api/audit` 拿最强的那把无作用域凭证也只有 405，行数一条没少。

### 4.6 没有按次调用的轨迹，延迟没有分位数 —— 已关闭

**当时的现象**：`deis tail` 流的是日志行，没有一条记录把「这次请求的地址、状态码、耗时、有没有抛异常」绑在一起。延迟存的是一个只升不降的高水位数值，所以「p99 是多少」回答不了——一次 30 秒的超时会把这个数字永久钉在 30 秒。

**做了什么**（`38fbeda` 产出，`1be047c` 给了读它的人）：

- deis-telemetry 多了一套 `TraceService`：推送、查询、跟随三个调用，和日志那套并排放，不混在一起。
- 节点每处理完一次调用就发一条轨迹——请求、队列批次、cron 触发、WebSocket 消息各算一次——记的是**平台做的判定**，所以「应用自己抛了」和「我们把它杀了」是两种不同的结局，超时、op 限流、内存、CPU 各有各的名字。
- 延迟从高水位改成直方图（`deis_runtime_isolate_execution_ms_bucket`，14 个桶，配 `_sum` 和 `_count`），Prometheus 的 `histogram_quantile` 能直接算分位数。
- 读的一头是 `deis trace`：按结局筛（`--outcome ok/app-error/timeout/rate-limited/memory-limit/cpu-limit/internal-error/failed`）、按类型筛（`--kind http/queue/cron/websocket`）、按状态码或状态码段筛、按时间段、按耗时下限、按轨迹号，也能 `--follow` 跟实时的。轨迹号和 `deis logs --trace-id` 是同一个号，所以从一条轨迹能直接跳到那次调用写的日志。

**半条**：采样有机制，没有配置位。节点默认把成功的调用也全记下来（采样率 1.0），被平台判失败的那些**任何采样率下都不丢**；但采样率和缓冲上限只能用环境变量 `DEIS_TRACE_SAMPLE_RATE` / `DEIS_TRACE_BUFFER` 调，节点的配置文件里没有对应的字段。deis-telemetry 那头留存是有默认的：`trace_retention_days = 3`，比日志的 7 天短，因为不管应用写不写日志，每次调用都会产生一条轨迹。

**没做的**：控制台里没有把这些数字画出来。

### 4.7 没有 compatibility date / flags —— 已关闭

**当时的现象**：没有任何机制让一个已部署的版本钉住它当初写作时的运行时语义。上一次升级依赖就同时改掉了三处可观察行为（权限里空列表的含义、空拒绝名单的含义、Web 全局的模块形态），整个机队在一次没人安排的重启里一起吃下。

**做了什么**：加了 compatibility date 与具名 flag，从项目文件一路到 isolate，并且挂了一条真实行为在上面。

**一句话是什么**：应用在 `.config.json` 里写 `"compatibilityDate": "2026-09-01"`（可选再写 `"compatibilityFlags"`），这一段进 bundle manifest，控制面在上传时校验并随部署下发，节点装载版本时解析成一份「答案表」，isolate 每次请求只问这份表里的一个布尔。

- **词表放在哪。** 日期类型、行为表（`FLAGS`）和解析器都在 `deis-bundle`，与 manifest 同处一地——构建写它、控制面校它、节点执行它、CLI 显示它，四方共用一份。加一条新行为是「表里加一行、枚举加一个成员、用它的地方问一次」，不动别的。
- **没写日期是什么意思。** 是**最老的那套行为**，而且永远是。给它今天的行为，就是这套机制本身要防的那种「无人安排的全机队变更」，而且下一次发布还会再来一遍；直接拒绝，则会在这套机制上线后的第一次节点重启里，把所有已部署应用一起打掉。代价是真的：没写日期的应用从此收不到任何会改变可观察行为的修复。所以没人对它保持安静——上传写一行 warn、每次下发写一行 warn、装载写一行 warn，`deis deploy` 每次都打印，`deis versions` 的 COMPAT 列直接印 `none (oldest)`。
- **写了本 build 不认识的日期是什么意思。** 拒绝。平台的知识止于自己的发布日（`PLATFORM_KNOWN_THROUGH`），所以「未来的日期」和「比本节点新的日期」是同一个问题，也用同一句话回答：构建时报错、上传时 400、控制面下发时拒绝、节点收到推送时在下载 bundle 之前就回 `success=false`（因为混合机队里控制面可能比节点新）。装作能提供，比拒绝更坏。
- **运行时在哪里问。** 只有一处：`CompatibilityProfile::is_on(Flag::X)`。日期比较只在版本装载时做一次，请求路径上是一次位测试，所以表长到三十行也还是能读。
- **挂了哪条真实行为。** 一个 handler 一次设两个 `Set-Cookie`（登录同时发会话 cookie 和 CSRF cookie，是最常见的写法），此前只有**最后一个**能到客户端，另一个被无声丢掉——响应头在离开 isolate 时走的是一张 map，而 `Set-Cookie` 恰好是 Fetch 规范里唯一不允许合并的头。现在 header 以「名值对列表」过界，日期在 `2026-09-01` 及以后的应用两个都发得出去，更早的（以及没写日期的）保持原样，并在节点日志里写清丢了几个、改哪一行就能全发。为什么挑它：老答案确实有人依赖——一个今天靠「后写的赢」来撤销前一个 cookie 的应用，改成两个都发之后，撤销那一条会真的生效，客户端上的 cookie 就没了。
- **看得见。** `deis deploy` 每次打印这个版本跑在哪一天下；`deis versions` 多了一列 COMPAT，写日期或 `none (oldest)`；控制面的版本接口把它单独提出来，不用去翻 manifest。

`scripts/demo.sh verify` 里有五条盯着它：CLI 两处都印出日期；production（写了日期）拿到 2 个 `Set-Cookie`；preview（同一份 handler，manifest 里没有日期）拿到 1 个，并且节点日志里有说明；上传一个日期是 2099 的 bundle 被 400 拒；上传一个不认识的 flag 也被 400 拒。

### 4.8 控制面里的路由没有任何人读 —— 已关闭

**当时的现象**：`/api/routes` 由控制面提供服务，`deis-proxy` 里 grep 不到一处读它，proxy 的域名表是从另一份配置来的。同一个问题（「这个请求该给哪个应用」）有两个真相来源，路径前缀路由和预览子域两件事都卡在这一根没接上的线上。

**做了什么**（`38fbeda`）：

- 控制面另开了一条给数据面用的路径 `/api/routing-table`。它和给控制台看的 `/api/routes` 不是同一个形状：这条带的是环境的**名字**（`production`、`pr-42`，也就是 `x-deis-environment` 这个头上真正传的那个值，不是内部主键）、带上**所有存在的环境**（哪怕它一条路由都没有，前门才好给它一个自动地址）、带一个整张表的版本号（拉的人不用逐行比对就知道有没有变）。这条路径的名字只在 `deis-wire` 里写了一次，两边都引它——之前两个互不依赖的 crate 各抄一份字面量，节点注册就因为这个悄悄坏过一次。
- deis-proxy 用**轮询**而不是推送：默认 5 秒一次，认的是它和控制面本来就共用的那把节点凭据。选轮询的理由是自愈——不管出了什么岔子（连接断了、控制面重启了、某次校验没过），下一次拉取就修好了；推送这条路最后都得再配一个周期性全量对齐才敢信，那对齐就是机制本身，推送只是优化。
- **控制面不可达的时候，最后一次收下的表继续生效，没有期限。** 拉失败只写 error、说清现在用的是哪张表、多久之前的，然后下一次接着试。数据面因为控制面连不上就开始拒绝流量，等于把一次管理面故障变成一次用户可见的故障，而控制面恰恰是最常被重启升级的那个进程。只有一种情况不同：从来没拉成功过的 proxy 手里没有表可留，它会退回到本机配置里的应用列表，也就是这个模块存在之前的行为。
- **要么整张要么不要。** 半张路由表会把线上请求发给错的应用，比一张旧表更糟。所以拉回来的那份文档是整份解析、整份校验、整份编译，最后靠一次指针交换换上去：一个请求要么看到换之前那张，要么看到换之后那张，没有看到一半的时刻。有一条不合法就整份拒绝，不做「跳过那一条」。
- 匹配顺序是：精确域名 → 通配域名（后缀越长越先，所以 `*.eu.example.com` 胜过 `*.example.com`）→ 自动预览地址 → 不写域名的路由（目录里的意思是「任意域名」，所以最不具体）。同一个域名内先比优先级、再比前缀长度，于是 `/api/v2` 胜过 `/api` 胜过 `/`，运维还能用 `priority` 手动翻盘。
- 自动预览地址：运维在 proxy 的配置里写 `routing.preview_zone`，每个环境就有了 `<环境>--<应用>.<域>` 这个地址，默认环境另外还有一个不带前缀的 `<应用>.<域>`。**分隔符是一个 DNS 标签里的 `--` 而不是点**，这是为了证书：一张通配证书只覆盖一层标签，`*.<域>` 能盖住 `pr-42--shop.<域>`，盖不住 `pr-42.shop.<域>`——后者要求每建一个应用就签一张 `*.shop.<域>`。不写 `preview_zone` 就整个关掉，一个地址也不凭空造。

**仍然要人手做的**：那条通配 DNS 记录。通配证书这一半在 4.12 关掉之后有了两条路：把 `include_preview_addresses` 打开，让每个环境地址各签一张（省事，但每张都占一次颁发额度）；或者仍然人手放一张 `*.<区>` 的通配证书（一张管全部，但通配只能走 `dns-01`，这个实现不说那套协议）。

### 4.9 没有 Node.js 兼容

**现象**：`node:` 内建模块和大部分 npm 包用不了。

**后果**：这一条要不要修取决于定位。Edge Canon 是照着 Web 标准面写的，坚持这一点是有道理的。但现实是很多库仍然要 `node:buffer` / `node:crypto`。

**大致代价**：大，且是产品决策不是工程决策。列在这里是为了让它成为一个明确的选择，而不是一个默认。

### 4.10 没有数据面 CLI —— 已关闭

**当时的现象**：`deis` 只有 `deploy` / `versions` / `rollback` / `status` / `secret` / `logs` / `tail` / `config`。想看一眼某个应用的 KV 里存了什么、想跑一条 SQL 修数据，只能直接去戳 gRPC，而 gRPC 还要带能力令牌。

**做了什么**（`38fbeda` 加了子命令，`1be047c` 补上了它们要的那个端点）：

- `deis kv get / put / delete / list`、`deis db query / execute`、`deis blob get / put / delete`。值可以从文件进、也可以写到文件里去，所以二进制内容不用经过 shell。
- 令牌不是人去铸的。控制面新开了 `GET /api/apps/<应用>/environments/<环境>/storage-token`，凭的是部署时用的那把 API key，答的是三样东西：这个令牌授权的租户名（`<应用>.<环境>`，也就是每次存储调用要回填在 `x-deis-tenant` 上的值）、deis-store 的地址、令牌本身。三样里少一样这个答案就没法用，所以缺任何一样都是拒绝而不是留空。控制面没配 deis-store 时答 409 并说清要去配哪个字段。
- 这一条是 `38fbeda` 里那半件没接上的事：子命令写好了，它们要调的那个端点控制面还没提供，所以第一版是「命令存在、一调就失败」。`1be047c` 补上了端点。

**后来补上的**：`deis blob` 现在还有 `list` 和 `head`，`get` 能带 `--offset` / `--length` / `--suffix` 取一段，`put` 和 `delete` 能带 `--if-match` / `--if-none-match` 做条件写（输了退出码是 3，见 4.3）。**没做的**：`deis db` 只有 `query` 和 `execute`，`batch` 与交互式事务只在应用里能用，命令行上没有。

### 4.11 只有墙钟上限，没有 CPU 时间上限 —— 已关闭

**当时的现象**：`ExecutionLimits` 只有墙钟和 op 速率。一个 handler 等一个慢上游 25 秒，和一个 handler 死算 25 秒，在限额上是一回事——但对节点的代价差了几个数量级：前者是一条停着的线程，后者是一个租户占着一颗核，这个节点上别的应用都排在后面。

**做了什么**（`38fbeda`）：

- `cpu_time_limit_ms` 和墙钟上限并排，默认 5 秒，由同一条看守线程执行，武装的粒度也一样——一次请求、一段 `waitUntil` 尾巴、一批队列消息、一次 cron、一条 WebSocket 消息，各算一段。
- 读的是被看守那条线程自己的 `/proc/<进程>/task/<线程>/stat`，用户时间加系统时间。**为什么不用更精细的 `clock_gettime`**：`CLOCK_THREAD_CPUTIME_ID` 只认调用它的那条线程，而看守线程恰恰不是被测的那条，所以得配 `pthread_getcpuclockid`；这个 crate 不依赖 `libc`，手写 `pthread_t` / `clockid_t` / `timespec` 三个类型声明在 `time_t` 宽度不一样的目标上是一类静默错读的隐患，而一条按错读的时钟执行的限额比一条粗糙的更坏。
- 代价是分辨率：`/proc` 里的数按调度时钟滴答计，实际上都是每秒 100 次，所以读数是 10 毫秒一跳。这也是为什么配置里的下限是 100 毫秒——量化误差最多占最小可配值的十分之一。
- 把 CPU 上限设得不比墙钟上限小，等于没设：一条线程烧掉的 CPU 时间不可能多过它占用的墙钟时间，墙钟那道闸永远先响。节点启动时按应用说出这件事，不留给人去撞。

**只在 Linux 上成立**：没有 `/proc/thread-self` 的地方（macOS、Windows、`/proc` 被藏起来的容器、3.17 以前的 Linux）读不到这条时钟。这种情况下启动时会以 **error** 级别说一声，点名哪条限额没在执行、还剩下哪条在执行——一条悄悄不生效的限额比一条从没提供过的更坏。
### 4.12 没有自动证书 —— 已关闭

**当时的现象**：证书是运维手动放置、手动续期的文件。每加一个域名都要人工介入，而且续期忘了就是线上事故——这正是**自建才需要**的东西，托管平台的用户从来不用想这件事。

**做了什么**：`crates/deis-proxy/src/acme/` 里做了一个 ACME（RFC 8555）客户端，默认关闭，`[tls.acme]` 打开。逐条说清选择和代价。

**为什么是 `http-01`，不是 `dns-01`**。证书颁发机构要先确认「你确实管得着这个域名」，办法有两种：一种是它来访问 `http://<域名>/.well-known/acme-challenge/<一串随机码>`，看你答得对不对；另一种是让你在 DNS 里放一条记录给它查。选前者，是因为这个代理本来就替它服务的每一个域名占着 80 端口，所以它自己就能答——不用多跑一个进程，不用和别的程序共用一个网页根目录，不用多一份东西保持同步。后者要一家一家接 DNS 服务商的接口，多一份凭证要轮换、多一个环节会坏。代价是**通配证书拿不到**：RFC 8555 只允许 `dns-01` 签发通配。所以 4.8 那批自动预览地址有两条路——把 `include_preview_addresses` 打开让每个地址各签一张，或者仍然人手放一张 `*.<区>`。

**给哪些域名签**。不另列清单，而是从这台机器**本来就在服务的两张表**里取：控制面推下来的应用域名，加上目录路由表里的具体主机名。所以在控制台里加一个域名，这台机器上不用改任何文件，证书自己就来了。另列一份清单的下场是有人忘了改它，而症状会是一个路由完全正常的域名握手失败。三类名字排除在外，各有各的理由：通配（`http-01` 根本签不了）、运维自己指定过证书文件的名字（那是他的决定，不该被自动的顶掉，而且**只要写了 `certificates` 就算，不管那个文件当下读不读得出来**——正在换证书的人不该被自动接管）、以及压根不是公网主机名的东西（IP 字面量、单标签名字），因为没有哪家 CA 会签，每试一次都白花一次额度。

**账号密钥和证书放在哪，重启会怎样**。都在 `storage_dir` 底下，再按**颁发机构的主机名分一层目录**。分这一层是为了挡一类很贵的错：先用测试环境签好，再把 `directory_url` 改成正式环境——如果不分层，进程重启后看见的是一批还有八十多天有效期的证书，判定「没到期，不用管」，于是一直拿浏览器不认的测试证书对外服务；测试环境的账号地址拿到正式环境去用，也是根本不存在的账号。分了层，改一次地址就是全部重新签，这才是运维改那一行时的本意。账号密钥只在第一次生成，之后一直复用：每次启动都新注册一个账号，会撞上颁发机构按 IP 计的注册限额，一台重启几次的机器自己就能把自己锁死。启动时先读目录，读到还没进入续期窗口的证书就什么都不做——**一次都不问 CA**。

**续期**。后台一条任务，默认每 12 小时过一遍，剩余有效期少于 `renew_before_days`（默认 30 天，证书本身 90 天）就重新签。失败按**还剩多少余地**分级别说：还有余地的记 `WARN`，剩余有效期已经少于 `alarm_before_days`（默认 7 天）的记 `ERROR`；两种都写清第几次失败、还剩几天、下一次什么时候试、是不是撞了限额。这一条是专门冲着最常见的死法去的——凌晨三点一次静默失败，两个月后网站过期。重试用翻倍退避，从 60 秒起，封顶 6 小时：最常见的失败原因是域名的 DNS 还没指过来，那要等人处理，一分钟试一次只是在 CA 和自己的日志里刷屏。

**默认打不到正式环境**。`directory_url` 的默认值是 Let's Encrypt 的**测试环境**（staging），启动时会以 `WARN` 说一句「现在用的是测试环境，浏览器不认，等签成功了再改成正式地址」。正式环境的限额按注册域名按周计、要不回来，所以正式地址得运维自己写一遍。`max_names` 再兜一层：路由表哪天异常长出几百个名字，也不会变成几百次签发——额度一旦花光，这个域名底下**所有**名字都签不出来，生产也在内。

**测试怎么做的**。`crates/deis-proxy/tests/support/acme_ca.rs` 是一个只跑在环回口上的假 CA。它不是个应付了事的桩：会用账号自己的公钥验 JWS 签名（所以把 DER 签名原样递上去这种错在这里就会被抓住，而不是几个月后在真 CA 那里）、会验保护头里的 URL 和一次性随机数、会验 CSR 里有没有 `subjectAltName`，也会真的回来抓一次挑战。它还可以被要求「所有订单都拒绝」或者「把挑战答案对错」，失败路径就是这么走出来的。八个集成测试跑的都是**真的 `deis-proxy` 进程**：签发并且真的用 TLS 取回那张证书、续期触发、CA 拒单后自己恢复、挑战校验失败、重启不重签也不重新注册、挑战路径只答自己发布过的令牌、以及没开 `[tls.acme]` 的实例一次都不联系 CA。`scripts/demo.sh` 里另有五条检查，把同一件事在整套演示里再走一遍。

**打开它要什么**：80 端口能从公网访问到（CA 只从这个端口抓挑战）、一个邮箱地址（证书快过期而续期一直失败时，CA 往这里写信，这是出事前唯一一封预警）、以及明写 `terms_of_service_agreed = true`——注册要带一条同意条款的声明，这个进程不替运维签字。

**顺手修掉的一个坑**：判断「这个名字有没有证书」原先是「读文件，读不出来就当没有」。这一句把「本来就没有」和「有但读不出来」混成一件事，后果是一个 PEM 坏掉的名字每一轮都重签一次，日志上一句都不说——而每一次重签都花掉这个域名一周额度里的一张。现在两者分开：只有两个文件都不在才叫「没有」，文件在而用不了会以 `WARN` 点名是哪个文件、什么毛病，再去要新的。

### 4.13 控制面与存储没有高可用

**现象**：控制面一个 SQLite 文件，存储一个 SQLite 文件，没有复制、没有故障转移。

**后果**：快照 / 恢复解决的是**备份**问题，不是**可用性**问题。存储进程挂了，所有应用的 `ctx.services.*` 全部不可用。

这一条也**不是关于地理规模的**：同机架三台机器就够，而现在不支持。

**大致代价**：大。

### 4.14 剩下那几个 ⚠️，都不够单开一条

第 2 节里还有四行是「有一半」，每一行缺的都只是一小块，凑在这里说，免得读的人在
4.1–4.13 里找不到它们而以为漏了：

- **队列消费的 `maxConcurrency` 不是并行**。清单里能写，节点也照做，可它限的是在手的
  批次数——已经从队列拉下来、还没结清的批次——不是同时在跑的批次数。一个应用在一个环
  境里、在每个节点上就是一条线程上的一个 isolate，处理函数只能一批一批地跑，这一点写
  多大的数字都改不了。它值多少：一个批次的一生是「拉下来 → 排队等运行时线程 → 跑 →
  确认」，只有第三段在 isolate 里，所以多留一个在手上，下一批在上一批跑完时已经拿到
  了。代价是租约：每一个在手的批次从拉下来那一刻就在花租约，排在队里等线程的那一批是
  在白花，花过头租约就到期，队列把同一批消息交给别人，同一份活做两遍。所以默认是 1，
  节点的上限是 8，并且启动时那条日志会把「不是并行」这句话直接写出来。真要并行消费，
  得让一个应用在一个节点上有多个 isolate，那是另一件事。
- **Cache API 存在 isolate 自己的内存里**。`caches.open(name)` 现在有了；缺的那一半是
  「跨节点共享」，而这一半不是补一个参数能补的——那是另起一个存储服务，它会带着一个存
  储服务的全部故障模式，落在每一次读缓存的请求路径上。所以这个取舍写进了 API，而不是
  只写在文档里：`caches.scope` 给出这个 store 的身份和它起始的时刻，应用把 `scope.id`
  记在自己缓存的东西旁边，就能分清两种「没读到」——一种是这一条被淘汰或过期了，store
  还是当初写进去的那个；另一种是 store 本身换了一个，之前写的全没了。这两件事对正确性
  的含义相反：前一种重新取一次就行，后一种意味着应用以为已经做过的事其实要重做。分不
  清的应用迟早会在发版那天出事。
- **预览地址是每个环境一个，不是每个版本一个**。地址指向环境，环境指向当前那一版。
  要做到「每一版一个地址」，得让路由能指向一个版本号而不是一个环境，这会动到目录的
  数据模型。
- **控制台只覆盖机队运维**：仪表盘、节点、控制通道、命令、事件、节点配置。目录那一
  半——应用、版本、环境、部署、密钥、路由——一页都没有。REST 全都有，`deis` 也全都
  能做，所以这是「点不到」，不是「做不到」。

## 5. Deislet 比 Cloudflare 强，或更适合自建的地方

### 5.1 出站流量由运维说了算，且默认拒绝

`fetch_policy.rs` 默认拒绝环回、RFC1918 私有地址、链路本地（包括云元数据地址 `169.254.169.254`）、唯一本地与链路本地 IPv6、组播、广播和保留段。判定的是**解析之后的地址**，不是主机名。DNS 重绑定被两层堵死：IP 字面量根本不碰解析器，域名走 `PolicyResolver`，它只返回策略已经接受的地址。每一次重定向跳转都重新过同一套规则。

Cloudflare 不给运维任何对应的旋钮——Worker 能访问什么，你说了不算。对一个**部署在自己内网里**的平台来说，这个区别是决定性的：没有这层，一个应用就是内网里的一个跳板。

### 5.2 真正的交互式 SQL 事务

Cloudflare 的 D1 只有 `batch()`（一批语句原子执行），做不到「读一行、根据结果决定、再写」——因为它是分布式的。我们是一台机器上一个租户一个 SQLite 文件，所以能做，评审那一轮做了：`BEGIN IMMEDIATE` 钉住一条连接，句柄归开它的租户所有，服务端硬超时到点回滚放连接（防止 handler 拿着事务去等一个慢上游，把这个租户唯一的写者一直占着）。

这是少数几个「自建反而可以做得更好」的地方之一。

### 5.3 每一个开 socket 的地方都过同一个判定点，而且是强制的，不是文档约定

deno_core 会把 op 表挂在 `globalThis.Deno.core` **和** `globalThis.__bootstrap.core` 两个地方。两个都删了，而且有测试同时敲这两扇门，断言 `op_net_connect_tcp` 够不着。评审那一轮新加的出站 `WebSocket` 也是自己写的 op，走同一个策略，而不是直接绑 `deno_websocket` 的客户端——因为那个客户端用自己的连接器，永远到不了 `fetch_policy`。

### 5.4 真 V8 inspector 接进生产 isolate

`_inspect:<app>` 路由到一个受令牌保护的 WebSocket，把 Chrome DevTools 直接桥进正在跑的 isolate。Cloudflare 给你 `wrangler dev` 里的 devtools；在生产 isolate 上单步调试，它不提供。

### 5.5 SQL 沙箱是靠 SQLite 自己的授权器守的

评审那一轮修的那个严重漏洞（见 6.2）的修法值得单独说：不是靠检查 SQL 文本关键字——那种检查一个前置注释就能绕过——而是装 SQLite 的授权器回调（authorizer），它在解析器**下面**，绕不过去。PRAGMA 用白名单而不是黑名单，因为黑名单会随版本变旧。

升级到 rusqlite 0.40 时又补了一处：这个库开始会报告「授权器没装上」这件事——以前它只能悄悄发生。deis-store 原来丢掉这个返回值，现在改成让这条连接直接失败。理由是：装不上还把连接发出去，等于发出一条看起来有防护、实际什么都不挡的连接，授权器本该拒绝的每一条语句——ATTACH 到别的租户的文件、`VACUUM INTO` 到任意路径、白名单之外的 PRAGMA——都会照跑不误。

### 5.6 节点不替应用继承自己的 `HTTP_PROXY`

`egress_proxy.rs`：这些变量在主线程读一次就从进程环境里删掉，免得 `deno_fetch` 悄悄把应用流量绕过去，然后显式交还给节点自己的三个客户端。这是托管平台永远不用想、自建运维必须想的一类意外。

### 5.7 一份源码编译到四个目标

`deis-build` 能把同一个项目产出 Cloudflare Workers、Deno Deploy、腾讯 EdgeOne 或本平台的可部署物，而且目标缺少某个已声明特性时**在构建期就拒绝**。Deislet 既是目的地也是一扇出门——Cloudflare 没有兴趣当后者。

### 5.8 数据是你的，且可检视

一租户一个 SQLite 文件、对象在本地磁盘、日志在你自己的 telemetry 进程、Prometheus 指标在你自己的端点。没有按次计费表，没有出网流量费。备份是 `deis-store snapshot`，用 `VACUUM INTO` 取一致快照——`cp -r` 一个 WAL 模式的库取不到，而且不会报错，只是恢复出来是错的。

## 6. 修过什么

分两段：评审过程中做的（6.1–6.3 加「其余」），和评审写完之后那四个提交做的（最后一节）。

### 6.1 平台声称的执行超时，对同步死循环完全不生效

每个 isolate 跑在自己的 OS 线程上，配一个 `current_thread` 的 tokio runtime。六条执行路径里有五条用 `tokio::spawn` 一个定时器来做超时。问题是：**那个定时器要等这条线程回来轮询才能跑**。

所以 `export default function handler() { while (true) {} }` 配 300 毫秒的预算，实测跑了 **75 秒还在跑**，一个核跑满，那条运行时线程永久失联。而任何一个用 `await` 空转来测超时的测试，从头到尾都是绿的。代码里甚至把这个洞写成了「超时机制的既有特性」而不是缺陷。

修法是把所有预算都改成一条**属于该 isolate 的 OS 线程**（V8 允许从任何线程 terminate）。修的过程中还踩到第二层：第一版仍然不生效，因为看门狗是在 `execute_script` **返回之后**才武装的——而 handler 的第一段同步代码就跑在 `execute_script` 里面，死循环根本没让它返回。改成先武装再执行之后，同样的死循环 0.43 秒被切断，同一个 isolate 随后继续正常服务。

### 6.2 一个租户能读写其他所有租户的数据库

`database.rs` 开头写着「文件级隔离是这里最省事的正确答案：一个租户没法指名另一个租户的表」。每一个分句都是假的。普通应用代码通过 `ctx.services.database` 做到了：

```js
const list  = await db.query("PRAGMA database_list");   // 得知自己的文件路径
const other = list[0].file.replace("attacker.production", "victim.production");
await db.execute(`ATTACH DATABASE '${other}' AS victim`);
await db.query("SELECT * FROM victim.secrets");         // 读到了别人的数据
await db.execute("INSERT INTO victim.secrets ...");     // 也写进去了
```

另外 `VACUUM INTO '/任意路径'` 能在存储进程能写的任何地方创建文件。

修法见 5.5。

### 6.3 内存上限从来没有被设置过

`IsolateSpec.memory_limit_mb` 会变成 V8 的 `heap_limits`，还挂了接近上限时终止执行的回调——这套机制是对的，而且**从来没有被喂过值**：它来自 `config.limits.as_ref().map(|l| l.memory_mb)`，而控制面和 bundle manifest 里没有任何一处填过 `ResourceLimits`。所以 `limits` 恒为 `None`，每个 isolate 都跑在 V8 的默认堆上。一个应用无限分配，撑爆的是整个节点进程，同进程里其他应用一起死。

超时和 op 速率都有平台级默认值可以被应用收窄，唯独内存没有默认值，于是形同虚设。现在有了。

### 其余

二进制体端到端（此前 `return fetch(<图片>)` 会损坏内容）、KV 值改字节并补齐 `list()`、SQL `batch()` 接进 JS、队列消息体改字节、存储调用带每租户能力令牌（非环回绑定且未配密钥时**拒绝启动**，而不是放行）、定时快照与保留策略、`waitUntil` 尾巴和 WebSocket 消息的执行预算、请求体上限（proxy 和节点两处）、出站 `WebSocket`、十个全局补齐、Cache API 不再破坏二进制、平台全局不能被改写并泄漏到同一 isolate 的下一个请求、入站帧类型不再由载荷自己声明。

以及一件方法上的事：写代码的一方和攻击的一方是分开的，不让人给自己判分。三轮下来对抗方一共打出 12 条，其中 1 条最高危、4 条高危——**没有一条是单元测试能发现的**，全部需要真的部署一个应用去打。

### 评审之后：四个提交

**`38fbeda`** 一次做了五条缺口的主体：静态站点的三个规则（4.4）、控制面路由接到前门（4.8）、数据面 CLI（4.10）、按次调用的轨迹与延迟直方图（4.6）、CPU 时间上限（4.11）。其中四条当时就完整了，第五条只做了一半，而**提交说明把这半件事直接写了出来**，没留给后来的人去发现。

**`1be047c`** 补的就是那一类：六个「写好了、测过了、注册过了，但没有任何一条请求走得到」的功能。找法是从上一波每一个新符号往外走，看有没有调用者——这条检查从此成了「关掉一条缺口」的收尾动作。六个分别是：

1. 静态站点的规则在装载时编译好了，可只有测试在调 `AssetBundle::serve`，HTTP 入口还在做一次朴素的索引查找。现在它按规则服务了，带路径也带查询串，`GET` 和 `HEAD` 都走。
2. `env.ASSETS.fetch()` 只有 Rust 那一半，没有 op、没有绑定。两样都补上了，并且 `ASSETS` 成了保留键，部署里同名的变量顶不掉它。
3. `deis_runtime_memory_cutoffs_total` 这个计数器从来没有人加过，于是运维从它读到的是「从来没有 isolate 撑爆过堆」——一个从没被写过的计数器和一个真的是零的计数器长得一模一样。现在接近上限那个回调会记它。
4. 清单里的 `limits` 块走到了消息里就停住了，节点建 `AppConfig` 时写的是 `limits: None`。现在会解出来并生效，而且每一个字段都对着节点自己的天花板夹一次——应用只能要求被管得更严，永远不能更松。
5. 轨迹有生产者、有存储、有查询接口，没有读的人。`deis trace` 是读它的那一头。
6. `deis kv/db/blob` 要调的那个存储令牌端点控制面没提供。现在提供了，认的是部署用的那把 API key。

这六条里有两条当时只走通了一半，是给演示加验证的时候撞出来的：

- 第 4 条。清单里的 `limits` 块从控制面到节点这一段是通的，可**没有任何构建器往清单里写过这个块**——`.config.json` 里的 `limits` 解析完就没人读，字段名（`timeout` / `maxPayloadSize` / `maxConcurrency`）和平台认识的那几个也对不上。于是真部署出来的应用仍然是 `limits: None`，6.3 那句「现在有了」在那时还只对了一半。现在项目里的 `limits` 会被译成清单里的同名块，块的定义搬到了 `deis-bundle`（构建写它、控制面校它、节点执行它，三方共用一份，而不是各写一份等着走样）。
- 第 5 条。轨迹有人读了，可节点记的时候用的是不带任何事实的那条重载，于是每一行的目标、方法和状态码都是空的——`deis trace` 甚至为此专门印一句「这些行既没有目标也没有状态，那是节点上的缺口，不是空结果」。现在请求路径把方法、URL、状态码和失败原因一并记进去，`deis trace` 的一行说得出「哪个请求、答了什么、怎么结束的」。

两条都由 `scripts/demo.sh verify` 盯着：上限那三项是照真请求和节点自己的日志判的，轨迹那一项开着流再发请求，跟到的必须是这一次调用。

**`b149c42`** 把前门从 pingora 0.5 升到 0.8.1。0.5 带着两个请求走私漏洞（CVSS 9.3），在一个多租户的边缘上，请求走私意味着一个租户的请求被交给另一个租户的应用，所以这是安全下限而不是偏好。**顺带堵上了我们自己的一个洞**：请求体上限原来对任何带 `Upgrade` 头的请求一律放行，而 pingora 0.5 只能从请求头判断这件事——于是一个普通的分块上传只要自称是升级，就能不受限地送到节点。0.8 能看到节点到底有没有回 101，现在问的是这个，两半都有对着真二进制跑的测试。

**`3753cb2`** 离开了 deno 的私有分支，改用发布版的 `deno_runtime` 0.266。那个分支存在的理由只有一条提交那么大，而它把运行时按在 31 个小版本之前，连带 hyper 0.14、rustls-webpki 0.102 和 aws-lc-sys 0.29 一起，中间夹着九条公告。`cargo audit` 这一次从 13 条降到 4 条（连同前两轮，是从 17 条降到 4 条），剩下的四条连同各自的理由写在 `.cargo/audit.toml` 里：三条是「链接进来了但应用够不到」，第四条（RSA 的 Marvin 计时侧信道，上游还没有修复版）应用够得到，那条写清了什么样的用法会暴露、暂时该改用什么。这次升级里和本文结论有关的两点：deno_fetch 现在会拿「名字解析出来的地址」再对一次拒绝名单，而拒绝名单写不出「例外」，所以运维用域名开的白名单会被这道兜底否掉——现在白名单里出现域名时就不装那份地址段兜底，机制仍然是策略本身（它在每个地址、每一跳上都认白名单）；另外 rusqlite 0.40 开始会报告「授权器没装上」，deis-store 从丢弃这个结果改成让这条连接直接失败——那个授权器就是租户的 SQL 沙箱（见 5.5），装不上还把连接发出去，等于发一条看起来有防护、实际没有的连接。

4. 控制面与存储的高可用（4.13）
