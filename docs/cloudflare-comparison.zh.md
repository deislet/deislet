# 功能性评审：Deislet 对照 Cloudflare Workers / Pages

日期：2026-08-30。对照的代码是 `fea1ab8`。

## 0. 这份评审的口径

Deislet 的定位是**私有化部署的小平台**：一个机房、几台机器，没有全球任播网络，没有几百个边缘节点。所以「我们节点少」不算差距——那是定位本身。这份评审只问一件事：

> 一个开发者按 Cloudflare Workers 的写法写好的应用，搬到 Deislet 上，**哪些地方会写不出来、跑不对、或者运维接不住**？

判定分三档：

- ✅ 有，且经代码核实
- ⚠️ 有一半，缺的部分写明
- ❌ 没有

每一条 Deislet 侧的判定都对着代码核过，不是按文档。这一点必须强调，因为这个仓库反复出现过「文档声称的能力代码里没有」——本轮就修了十几处。

---

## 1. 结论

第 2 节那八张表一共 73 行：**✅ 39、⚠️ 7、❌ 27。**

27 个「没有」里，绝大多数分成两堆：一堆是 **Cloudflare 在卖它自己的机器**（Workers AI、Vectorize、Hyperdrive 之类），自建装机缺的是硬件不是平台功能；另一堆是**多接入点网络才有的属性**（第 3 节列了 11 项）。剩下**13 项是自建用户真会撞上的**，第 4 节逐条展开。

按撞上的概率和痛感排，前五个是：

1. **流式响应过不了 isolate 边界** —— Server-Sent Events 写不出来，大文件代理会整个进内存
2. **没有 Durable Objects 或任何协调原语** —— 计数器、锁、房间、在线状态，一个都做不了
3. **对象存储只有 put/get/delete** —— 不能列举、不能断点续传、不能按字节范围取
4. **静态站点缺 `_redirects` / `_headers` / SPA 兜底** —— 所有静态站点生成器都会吐这两个文件
5. **没有账号体系** —— 一把 API key 通吃所有应用的所有操作，第二个人加进来就没法分权

后面还有八条，第 4 节逐条展开。

需要说明的是：这个清单是**这一轮修完之后**的清单。评审开始时的前五名里有三条（`waitUntil` 不受限、没有事务、请求体没有上限）已经在本轮修掉了，还顺带修掉了一个跨租户读写数据库的严重漏洞。第 6 节列了本轮做了什么。

## 3. 因为是单集群，所以本来就不需要的

这 11 项不是差距，列出来是为了避免后来者把它们误当成待办：

- **灰度百分比放量**。CF 需要它是因为一次变更同时落到几百个机房，得有统计意义的爬坡。这里部署只到少数几台机器，回滚是挪指针、一秒完成，「蓝绿 + 秒级回滚」在这个规模上覆盖了同样的需求。（如果机队真长到几十台，按节点分批仍然值得做；按百分比那套机器不值得。）
- **Smart Placement / 区域放置提示**。只有一个地方能跑，没什么可决定的。
- **任播、全局负载均衡、地理调度、Argo**。都是多接入点网络的属性。
- **Tiered Cache / Cache Reserve**。它们存在是为了减少跨机房回源。这里源站就在旁边。
- **Durable Object 的司法辖区与位置提示**。运维已经选好机器在哪了。
- **Workers for Platforms / dispatch namespace**。那是「大规模托管别人的不可信 Worker 并计费」的产品。自建装机真正需要的那部分是 RBAC，已单列为真实缺口。
- **免费版 / 付费版的限额分层与账号级日配额**。没有计费套餐要区分。
- **多区域存储复制与只读副本**（D1 read replication、R2 jurisdictions）。单集群没有意义；单集群内为了可用性做复制是另一回事，已单列为真实缺口。
- **Workers AI 与 Vectorize 作为一等绑定**。这两个是 CF 在卖自己的 GPU 机队和索引服务。自建用户通过 `fetch` 调外部推理 API 今天就能用，而且我们的出站策略让这个调用是受管控的。缺的是硬件，不是平台功能。
- **Hyperdrive 的全球连接池层**。它的价值是在每个机房旁边握着热连接，免得悉尼的 Worker 现开一条到弗吉尼亚的 Postgres 会话。单集群里数据库就在同一个局域网。

## 4. 真正要紧的缺口

按「自建用户撞上的概率 × 撞上之后有多难受」排序。每条给出：现象、后果、今天只能怎么办、大致代价。

### 4.1 流式响应过不了 isolate 边界

**现象**：`ReadableStream` / `WritableStream` / `TransformStream` 三个构造器都在，handler 内部用它们完全正常。但请求体和响应体在跨 Rust↔JS 边界时是**一整块完整的字节数组**（`isolate.rs` 的 `PendingRequestBody` / `PendingResponseBody`）。

**后果**三条，一条比一条难受：

1. **Server-Sent Events 写不出来**。SSE 的做法是返回一个永不结束的响应体，一条条往外推。这里 handler 必须先把整个响应体凑齐才能返回，所以推不出去。任何「实时进度条」「流式 AI 回答」都得改用 WebSocket 绕。
2. **代理大文件会整个进内存**。`return fetch("https://.../big.iso")` 会把整个文件读进节点内存再吐出去。有了本轮加的内存上限，这不会再撑爆节点了——但会变成这个应用自己被杀掉。
3. **最阴的一条**：因为三个构造器都在，照着流写的代码**能编译、能跑、行为却是错的**——它不报错，只是不流。

**今天只能怎么办**：分块下载 + WebSocket 推送，或者把大文件直接放静态资源让 asset-first 那条路服务（那条路是流式的）。

**大致代价**：中到大。要把 op 边界从「一块字节」改成「一个可读资源」，`deno_core` 有 `ResourceId` 这套东西可以用；但 dispatcher、pool、isolate 三层的消息类型都要跟着改，Cache API 和 KV 也要想清楚要不要跟。

### 4.2 没有 Durable Objects，也没有任何协调原语

**现象**：没有任何东西能保证「同一个键的操作被串行地、在同一个地方执行」。

**后果**：一整类东西做不了——串行计数器、分布式锁、每实体状态机、多人协作 / 房间、跨连接的 WebSocket 在线名册。

这一条**不是单集群的后果，恰恰相反**：单集群是最容易做单实例 actor 的地方，不需要任何全局路由。

**今天只能怎么办**：交互式事务（本轮新增）能覆盖「读—判断—写」这一类；剩下的没有替代。

**大致代价**：大。要有对象标识到节点的路由、每对象的单线程执行、每对象的持久状态，以及一个应用调用另一个对象的调用路径。

### 4.3 对象存储只有 put / get / delete

**现象**：`blob.proto` 就三个方法，`GetRequest` 只带一个 key。

**后果**：不能翻页列举一个桶、不能按字节范围取（所以视频拖动进度条不行、大文件断点续传不行）、不能做条件写（compare-and-set）、不能挂自定义元数据。对自建用户来说，这是「对象存储」和「一个你必须已经知道名字才能取的地方」之间的区别。

**大致代价**：中。元数据已经在 SQLite 里，list 和 head 主要是加 RPC；range 读要动流式下载那条路（和 4.1 相关）；条件写要一个原子的 compare-and-set。

### 4.4 静态站点缺 `_redirects` / `_headers` / SPA 兜底

**现象**：三个都没有。

**后果**：地球上每一个静态站点生成器都会吐 `_redirects` 或 `_headers`。而这个平台是当作「自建版 Pages」宣传的。今天想给一个静态路径加一条重定向，或者加一个 `Cache-Control`，就得写一个函数——而这恰好绕开了 asset-first 的全部意义（本来这个请求根本不该进 isolate）。SPA 兜底（所有未命中路径回 `index.html`）更是单页应用的默认需求。

**大致代价**：小。`deis-bundle` 在构建时解析这两个文件，塞进 manifest；`AssetIndex` 查找时套用规则。是这份清单里性价比最高的一条。

### 4.5 一种资源只能挂一个绑定，且没有账号体系

两件事，凑在一起说是因为它们都属于「第二个人 / 第二个用途加进来的时候就不够用了」。

**具名绑定**：一个 `(应用, 环境)` 只有一个 KV、一个数据库、一个对象存储、一个默认队列。冷热数据分开、一个应用挂两个桶，没有任何表达方式。（`ServiceConfig` 上的 `namespace` 和 `connectionString` 本轮删掉了——两个字段都在，但全仓没有一个读者，留着是个陷阱：作者能设，没人读。）

**账号体系**：一把扁平的 API key 授予对所有应用的所有操作。第二个人或第二个团队用上这套装机的那一刻，没有任何办法限定范围或者归因，而部署路径上是带着解密后的密钥走的。

**大致代价**：具名绑定中等（要动 manifest、控制面数据模型、绑定注入）；RBAC 中到大。

### 4.6 没有 per-invocation trace，延迟没有分位数

**现象**：`deis tail` 流的是日志行。没有一条记录把「这次请求的 URL、状态码、耗时、有没有抛异常」绑在一起。延迟存的是一个只升不降的高水位 gauge。

**后果**：「把最近失败的请求列给我看」这个问题回答不了——只能去日志里翻。「p99 是多少」也回答不了，因为高水位不是分位数：一次 30 秒的超时会把这个数字永久钉在 30 秒。

**大致代价**：小到中。trace 事件是一个新的 telemetry 记录类型 + 每次调用发一条；延迟换成直方图是改 `metrics.rs` 的一个类型。

### 4.7 没有 compatibility date / flags

**现象**：没有任何机制让一个已部署的版本钉住它当初写作时的运行时语义。

**后果**：将来任何一次全局面或 `Response` 处理的改动，都是**整个机队的破坏性变更，没有渐进通道**。本轮一次性绑了十个全局，如果哪天要收回一个，就没有平滑的办法。

**大致代价**：中。manifest 里加一个日期，isolate 构建时按日期分支。难的不是机制，是从现在开始必须一直守住它。

### 4.8 控制面里的路由没有任何人读

**现象**：`/api/routes` 由控制面提供服务（`api/catalog/mod.rs:118`），`deis-proxy` 里 grep 不到一处读它。proxy 的域名表是**从另一份配置**来的。

**后果**：同一个问题（「这个请求该给哪个应用」）有两个真相来源。路径前缀路由和预览子域名两件事都卡在这一根没接上的线上——这也是为什么 2.4 里「每个版本一个预览 URL」是 ⚠️ 而不是 ✅。

**大致代价**：小。是一条链接，不是一个功能。

### 4.9 没有 Node.js 兼容

**现象**：`node:` 内建模块和大部分 npm 包用不了。

**后果**：这一条要不要修取决于定位。Edge Canon 是照着 Web 标准面写的，坚持这一点是有道理的。但现实是很多库仍然要 `node:buffer` / `node:crypto`。

**大致代价**：大，且是产品决策不是工程决策。列在这里是为了让它成为一个明确的选择，而不是一个默认。

### 4.10 没有数据面 CLI

**现象**：`deis` 有 `deploy` / `versions` / `rollback` / `status` / `secret` / `logs` / `tail` / `config`，没有 `deis kv` / `deis db` / `deis blob`。

**后果**：想看一眼某个应用的 KV 里存了什么、想跑一条 SQL 修数据，只能直接去戳 gRPC，而 gRPC 现在还要带能力令牌。运维日常会天天撞。

**大致代价**：小。服务端 RPC 都在，是加子命令。

### 4.11 只有墙钟上限，没有 CPU 时间上限

**现象**：`ExecutionLimits` 只有 `timeout_ms`（墙钟）和 op 速率。

**后果**：一个 handler 等一个慢上游 25 秒，和一个 handler 死算 25 秒，在限额上是一回事——但对节点的代价差了几个数量级。CF 把 CPU 时间单列出来正是为了这个。

**说明**：本轮之前这一条是「墙钟上限也不生效」，已经修好（见 6.1）。现在是「墙钟生效了，CPU 时间还没有单独的闸」。

**大致代价**：小到中。`clock_gettime(CLOCK_THREAD_CPUTIME_ID)` 在看门狗线程里采样即可，机制已经有了。

### 4.12 没有自动证书

**现象**：证书是运维手动放置、手动续期的文件（`TLS_SETUP.md`）。

**后果**：每加一个新域名都要人工介入，而且续期忘了就是线上事故。ACME 客户端恰恰是**自建才需要**的东西——CF 用户从来不用想这件事。

**大致代价**：中。接一个现成的 ACME 库，加上 HTTP-01 挑战要走 proxy 那一跳。

### 4.13 控制面与存储没有高可用

**现象**：控制面一个 SQLite 文件，存储一个 SQLite 文件，没有复制、没有故障转移。

**后果**：快照 / 恢复解决的是**备份**问题，不是**可用性**问题。存储进程挂了，所有应用的 `ctx.services.*` 全部不可用。

这一条也**不是关于地理规模的**：同机架三台机器就够，而现在不支持。

**大致代价**：大。

## 5. Deislet 比 Cloudflare 强，或更适合自建的地方

### 5.1 出站流量由运维说了算，且默认拒绝

`fetch_policy.rs` 默认拒绝环回、RFC1918 私有地址、链路本地（包括云元数据地址 `169.254.169.254`）、唯一本地与链路本地 IPv6、组播、广播和保留段。判定的是**解析之后的地址**，不是主机名。DNS 重绑定被两层堵死：IP 字面量根本不碰解析器，域名走 `PolicyResolver`，它只返回策略已经接受的地址。每一次重定向跳转都重新过同一套规则。

Cloudflare 不给运维任何对应的旋钮——Worker 能访问什么，你说了不算。对一个**部署在自己内网里**的平台来说，这个区别是决定性的：没有这层，一个应用就是内网里的一个跳板。

### 5.2 真正的交互式 SQL 事务

Cloudflare 的 D1 只有 `batch()`（一批语句原子执行），做不到「读一行、根据结果决定、再写」——因为它是分布式的。我们是一台机器上一个租户一个 SQLite 文件，所以能做，本轮做了：`BEGIN IMMEDIATE` 钉住一条连接，句柄归开它的租户所有，服务端硬超时到点回滚放连接（防止 handler 拿着事务去等一个慢上游，把这个租户唯一的写者一直占着）。

这是少数几个「自建反而可以做得更好」的地方之一。

### 5.3 每一个开 socket 的地方都过同一个判定点，而且是强制的，不是文档约定

deno_core 会把 op 表挂在 `globalThis.Deno.core` **和** `globalThis.__bootstrap.core` 两个地方。两个都删了，而且有测试同时敲这两扇门，断言 `op_net_connect_tcp` 够不着。本轮新加的出站 `WebSocket` 也是自己写的 op，走同一个策略，而不是直接绑 `deno_websocket` 的客户端——因为那个客户端用自己的连接器，永远到不了 `fetch_policy`。

### 5.4 真 V8 inspector 接进生产 isolate

`_inspect:<app>` 路由到一个受令牌保护的 WebSocket，把 Chrome DevTools 直接桥进正在跑的 isolate。Cloudflare 给你 `wrangler dev` 里的 devtools；在生产 isolate 上单步调试，它不提供。

### 5.5 SQL 沙箱是靠 SQLite 自己的授权器守的

本轮修的那个严重漏洞（见 6.2）的修法值得单独说：不是靠检查 SQL 文本关键字——那种检查一个前置注释就能绕过——而是装 SQLite 的 authorizer 回调，它在解析器**下面**，绕不过去。PRAGMA 用白名单而不是黑名单，因为黑名单会随版本变旧。

### 5.6 节点不替应用继承自己的 `HTTP_PROXY`

`egress_proxy.rs`：这些变量在主线程读一次就从进程环境里删掉，免得 `deno_fetch` 悄悄把应用流量绕过去，然后显式交还给节点自己的三个客户端。这是托管平台永远不用想、自建运维必须想的一类意外。

### 5.7 一份源码编译到四个目标

`deis-build` 能把同一个项目产出 Cloudflare Workers、Deno Deploy、腾讯 EdgeOne 或本平台的可部署物，而且目标缺少某个已声明特性时**在构建期就拒绝**。Deislet 既是目的地也是一扇出门——Cloudflare 没有兴趣当后者。

### 5.8 数据是你的，且可检视

一租户一个 SQLite 文件、对象在本地磁盘、日志在你自己的 telemetry 进程、Prometheus 指标在你自己的端点。没有按次计费表，没有出网流量费。备份是 `deis-store snapshot`，用 `VACUUM INTO` 取一致快照——`cp -r` 一个 WAL 模式的库取不到，而且不会报错，只是恢复出来是错的。

## 6. 本轮修了什么

评审过程中做了三轮修复。挑三条最重要的说，其余在提交记录里。

### 6.1 平台声称的执行超时，对同步死循环完全不生效

每个 isolate 跑在自己的 OS 线程上，配一个 `current_thread` 的 tokio runtime。六条执行路径里有五条用 `tokio::spawn` 一个定时器来做超时。问题是：**那个定时器要等这条线程回来轮询才能跑**。

所以 `export default function handler() { while (true) {} }` 配 300 毫秒的预算，实测跑了 **75 秒还在跑**，一个核跑满，那条运行时线程永久失联。而任何一个用 `await` 空转来测超时的测试，从头到尾都是绿的。代码里甚至把这个洞写成了「超时机制的既有特性」而不是缺陷。

修法是把所有预算都改成一条**属于该 isolate 的 OS 线程**（V8 允许从任何线程 terminate）。修的过程中还踩到第二层：第一版仍然不生效，因为看门狗是在 `execute_script` **返回之后**才武装的——而 handler 的第一段同步代码就跑在 `execute_script` 里面，死循环根本没让它返回。改成先武装再执行之后，同样的死循环 0.43 秒被切断，同一个 isolate 随后继续正常服务。

### 6.2 一个租户能读写其他所有租户的数据库

`database.rs` 开头写着「文件级隔离是这里最省事的正确答案：一个租户没法指名另一个租户的表」。每一个分句都是假的。普通应用代码通过 `ctx.services.database` 做到了：

```js
const list  = await db.query("PRAGMA database_list");   // 得知自己的文件路径
const other = list[0].file.replace("attacker.production", "victim.production");
await db.execute(`ATTACH DATABASE '${other}' AS victim`);
await db.query("SELECT * FROM victim.secrets");         // 读到了别人的数据
await db.execute("INSERT INTO victim.secrets ...");     // 也写进去了
```

另外 `VACUUM INTO '/任意路径'` 能在存储进程能写的任何地方创建文件。

修法见 5.5。

### 6.3 内存上限从来没有被设置过

`IsolateSpec.memory_limit_mb` 会变成 V8 的 `heap_limits`，还挂了接近上限时终止执行的回调——这套机制是对的，而且**从来没有被喂过值**：它来自 `config.limits.as_ref().map(|l| l.memory_mb)`，而控制面和 bundle manifest 里没有任何一处填过 `ResourceLimits`。所以 `limits` 恒为 `None`，每个 isolate 都跑在 V8 的默认堆上。一个应用无限分配，撑爆的是整个节点进程，同进程里其他应用一起死。

超时和 op 速率都有平台级默认值可以被应用收窄，唯独内存没有默认值，于是形同虚设。现在有了。

### 其余

二进制体端到端（此前 `return fetch(<图片>)` 会损坏内容）、KV 值改字节并补齐 `list()`、SQL `batch()` 接进 JS、队列消息体改字节、存储调用带每租户能力令牌（非环回绑定且未配密钥时**拒绝启动**，而不是放行）、定时快照与保留策略、`waitUntil` 尾巴和 WebSocket 消息的执行预算、请求体上限（proxy 和节点两处）、出站 `WebSocket`、十个全局补齐、Cache API 不再破坏二进制、平台全局不能被改写并泄漏到同一 isolate 的下一个请求、入站帧类型不再由载荷自己声明。

以及一件方法上的事：写代码的 agent 和攻击的 agent 是分开的，不让人给自己判分。三轮下来对抗方一共打出 12 条，其中 1 条 critical、4 条 high——**没有一条是单元测试能发现的**，全部需要真的部署一个应用去打。
