# 机器通道迁移之后仍然存在的共享密钥

> 状态：待办清单，不是决策记录。决策见 [ADR-025](../adr/025-machine-identity-and-capabilities.md)，
> 本轮的实施过程见[阶段分析](../archive/phase-analysis-2026-09-03.zh.md)。

## 这份文档为什么存在

`node_preshared_keys`（舰队级共享口令）已经被每实例 mTLS 身份替换完毕：这个配置项在代码里
已经不存在，控制面读到还写着它的配置文件会直接拒绝启动。**节点与控制面之间**不再有共享口令
—— 但这套安装**仍然在用别的全场通用密钥**。

把这条写下来，是因为它极易被读成更强的结论。「舰队口令没有了」和「共享密钥模式结束了」
差着好几项工作，而后者是一个会让人停止加固的句子。任何对外描述安全态势的文字，
都必须同时说出下面这张表还没清空。

## 还在的东西

| 凭证 | 在哪里 | 它开的是什么门 | 现在的形态 |
|---|---|---|---|
| inspector 会话令牌 | `crates/deis-runtime/src/app/manager.rs` | 一个调试会话 | **不属于这一类**：节点自己铸造、驻留内存、会过期，与舰队无关。列在这里只是为了说明它为什么不该跟着一起删 |

deis-store 与 deis-queue 的 `auth_secret`（以及控制面的 `storage_auth_secret`、由它 HMAC 派生的 storage token）已经删掉：两者只认 control 用 Ed25519 签发、15 分钟过期、可按 `jti`/节点/租户吊销的 capability，公钥与签名吊销名单用各自的机器身份经 mTLS 从 machine channel 拉取；节点只能为分配给自己的租户申领。deis-telemetry 的 `auth_secret` 同样已经删掉：遥测只认 control 签发的 capability，写入用 `ingest`、读取用 `read`，都按租户限定，节点经机器通道申领、CLI 向 control 申领并记审计，没有不鉴权的模式。见 `docs/trust-boundaries.md` 的「Telemetry」一节。

## 还剩下的怎么收

- 主密钥是单机持有的静态值，不是全场共享的应用凭证；收敛它要走 ADR-025 的后续阶段，
  不是把它换成另一个静态值。
- 后端迁移管理凭证 `migration_admin_token` 已随身份迁移子系统一起删除（2026-09-28）。
- 动它们之前先看 `docs/adr/025-machine-identity-and-capabilities.md` 的非目标一节：
  那里明确禁止为 legacy 凭证发「按节点伪造的衍生 token」，这类捷径在这几处尤其诱人。

## 附：一条与共享密钥无关、但同轮查实的运行缺陷

> 放在这里是因为它没有别的归处，而它是靠一次事故发现的。**已查实，不是推测**；
> 修复需要改动部署状态机，那是产品决策，见末尾的三个待定问题。

### 现象

2026-09-11 的一次门禁运行中，一个额外注册的节点在部署投递期间因注册过期被移出舰队。此后
该应用 production 环境的**每一次部署都返回 409「deployment plan ... is already in progress」**，
跨三次独立的 verify 运行、超过 30 分钟没有自行解开。同一份代码在节点全程在位的干净运行里 97 项全过。

### 查实的机制

- **409 的出处**：`catalog/store.rs` 的 `create_deployment_plan` 在写事务里拒绝「该环境已有
  计划处于非终态」。非终态有六个，终态只有 `active` / `failed` / `aborted` 三个。
- **target 集合在建计划时冻结，并且故意把失联节点算进去**（`delivery/mod.rs` 的
  `serving_target_ids`）—— 这是既定设计，为的是让回执能点名「这台没收到」。
- **离队 target 的推送永远是失败，不是跳过**：deliverer 在**拨号之前**就把 departed / contested
  的 target 翻译成 `Transport` 错误。而判定成功的谓词是全称的（`failed` 必须为空）。
- **两条永久卡死路径**：pre-commit 卡在 `aborting`（补偿推不完就不迁移），post-commit 卡在
  `activating`/`reconciling`/`degraded` —— 后者**唯一的出口是 `active`**，而 `active` 要求每个
  冻结 target 都有 `active` 观察记录，观察记录只在协调者推送成功时写入。两条路径对外表现相同。
- **协调者租约帮不上忙**：它保护的是「协调者进程死了」。本案里协调者每轮都正常跑完并主动释放，
  两秒后又被重新认领 —— 接管机制工作得很好，它每两秒忠实地把同一个注定失败的动作再做一遍。
  **没有尝试上限、没有退避、没有截止时间。**
- **reaper 不管部署计划**，从来没打算管。把节点移出舰队的是节点健康轮询，它不查、不通知、不释放任何计划。

**唯一的自愈条件是那个节点用同一个 id 重新注册。** 真正重启的机器会自愈；一个再也不会回来的
id 不会。运维手上唯一的杠杆 `DELETE .../registration` 反而把失败从 `Transport` 变成
`UnknownNode`，依然是失败，解不开。

### 一条已排除的怀疑

失败与本轮的 mTLS 改动无关。那个幽灵节点是用证书注册、未上报 mTLS 管理地址的，所以回落到
「第一把钥匙 + 明文地址」，而那个地址正是真实节点的管理面。**它在册期间推送本应成功**；
266 次失败全部发生在它被判定离队之后，是上面那条「离队即失败」的既有行为。

### 修的时候要守住什么

「暂时联系不上」和「已被判定离开舰队」是两件事，**不能混**：
- 联系不上但还在名单上 —— 继续等是对的，现行行为不要动。
- 已经离队 —— 无限等是错的。但「一离队就放弃」会犯反向错误：默认注册 TTL 是 90 秒，
  一台机器重启 91 秒就会离队。所以判据必须是**离队 + 一个宽裕的截止时间**，不是二者之一。
- 放弃时**不能假装那个 target 确认过**。必须留下「这个 target 从未被对账」的持久证据，
  否则下一次事故里没人能解释那台机器上为什么有一个陌生的 generation。

### 附带发现

`deployments.rs` 里 `let _ = abort_prepared_plan(...)` 丢掉了返回值。补偿没做完时 API 依然回
一个干净的 503「production 指针未改变」，调用方**完全看不出还有一个计划留在 `aborting` 里占着
环境**。这就是为什么这个卡死要到「下一次部署」才暴露。

### 已修（2026-09-11）

上面那三个待定问题里，第一个靠读代码定死了，另两个用一条**只对「已离队」生效**的截止时间
绕开了，不需要新增终态：

- **状态机本身没动。** `activating` / `reconciling` / `degraded` 的唯一出口仍是 `active`，
  仍然要求每一个冻结目标都上报精确 generation。改的是**什么算「settled」**：一个已经
  不在舰队名单上、并且超过截止时间的目标，被写下一条 `abandoned` 观测行，
  然后计入 settled。计划的 note 里也会写明有几个目标是被放弃的，
  **不是被确认的** —— 这条是当初记下的硬约束，守住了。
- **只对「已离队」生效。** 还在名单上但推送失败的目标，照旧无限等 —— 那是一台有问题的
  机器，放弃它等于把运维最该看见的东西盖住。
- **截止时间可配**：`deployment_target_abandon_after_secs`，默认 600 秒。文档里写死了
  硬约束：必须明显大于 `node_registration_ttl_secs`（默认 90）加一次正常重启。
- **放弃推送不等于放弃部署。** 节点每次启动都向控制面要清单，所以真回来的机器会自己
  装上当前版本。丢的是确认，不是投递 —— 这也是敢设一个不太长的默认值的理由。

同一轮里补掉了两个结构相同、但当时没被看见的洞：

1. **代理侧。** `reconcile_plan` 在「所有代理都上报了吗」那道门上**提前 return**，
   根本走不到终结判定。所以只在终结判定里放弃是不够的 —— 放弃必须发生在那道门**之前**，
   而且代理的「在不在」是另一个问题（一个活着的会话，不是舰队名单上的一行）。
2. **`aborting` 侧。** 这是同一个洞从另一头进来：一个 pre-commit 的计划，
   要每个冻结目标都确认收到 abort 才会转 `failed`，而离队的机器什么都不会确认，
   于是卡在 `aborting` —— 同样在拒绝下一次部署的名单里，而且这个计划**连什么都没改过**。
   判据相同；观测行写 `abandoned` 而不是 `aborted`，因为没人看见那台机器丢掉预备版本。
   真实情况是它手上有一个从未激活的 staged 版本，它自己下一次对账就会丢掉 ——
   补偿照样发生，只是这个计划看不到。

三条路径各有一条回归测试：先复现 409、验证不提前放弃、过期后计划终结、
观测行是 `abandoned`、环境重新可部署。

### 三个待定的产品决策（已由上面一节回答）

1. 观察到的那次究竟卡在 `aborting` 还是 `reconciling`？两者 409 相同、都同样永久，**修法不同**
   （前者补完 `aborting→failed`，后者需要新增一个诚实的 post-commit 终态）。
2. 把 post-commit 计划从 409 的阻塞名单里摘掉是否安全？一个被取代的旧计划，其 reconcile 循环
   仍在向掉队节点推它自己的 routing generation —— 若那台节点在新计划提交后才回来，可能先收到旧的。
3. 截止时间取多少？硬约束是必须明显大于 `node_registration_ttl_secs`（默认 90 秒）加一次正常重启，
   具体长度是运维对「一台机器多久没回来算真没了」的判断，应当可配置。

### 同轮观测到的一条较轻的脆弱性

`scripts/demo.sh` 的 `check_dynamic_node_registration` 一旦在注册与注销之间中断，会把一个幽灵
节点留在舰队上，让此后所有部署报「部分失败」。门禁运行被中断的代价因此不止是「这次没跑完」——
它会把环境留在让后续运行都失真的状态里。

## 附二：舰队口令下线之后剩下的清理（2026-09-11）

> 这一节是在「把 `node_preshared_keys` 从 demo 的每一份配置里彻底删掉、并让 97 项验收在
> **全场没有任何一处配置过舰队口令**的前提下通过」这一步之后写的。到这一步为止，
> 舰队口令**已经不再是任何一扇门的钥匙**；剩下的都是残留物的清理，不是安全问题。
> 分开写，是因为把「清理没做完」读成「洞还在」会让人重复已经做过的工作。

### 现在的真实状态

- `deis-control` 的 `node_preshared_keys` 变成可选（`serde(default)`）。配了 `[machine]`
  机器通道时，空列表**不再临时铸一把钥匙** —— 铸一把没有任何节点配置的钥匙，只会产出一个
  谁也认证不了的凭证，外加一个搞不清当前生效的是哪套机制的运维。
- `deis-wire` 的 `[control] secret` 变成 `Option<String>`。**不写**是一种配置（该进程用证书
  证明自己）；**写了但留空**仍然被拒（那是运维忘了填，不是一种选择）。
- deis-proxy 增加一条跨段校验：`[control]` 在、而 `secret` 与 `[machine_identity]` 两者都没有
  的进程**启动即失败**。否则它会正常起来、正常监听，然后在整个生命周期里每一次注册和每一次
  路由表拉取都被拒 —— 而没有任何一行日志会说这是为什么。

## 附三：证书解决了「谁在打电话」，没解决「他该听到多少」（2026-09-11 查实）

这一条是文档扫尾时被发现、随后在代码里核实的。它不是共享密钥问题，但它决定了
**上面那一整轮工作到底把风险降低了多少**，所以必须和那轮结论写在一起。

### 事实

`crates/deis-control/src/api/catalog/assignments.rs` 的 `assignments_for(state, node_id, base)`
第一行就是 `state.store.list_assignments()` —— **取的是整个目录**。传进来的 `node_id`
此后只出现在日志里，不参与任何过滤。也就是说：

> 任何一台节点问「我该跑什么」，拿到的都是**全平台每一个环境**的清单，
> 其中含每个环境的**解密后密钥**和每个租户的**存储 capability token**。

### 这对上一轮结论意味着什么

机器通道换成 mTLS 之后，**「谁在打电话」这个问题有了真答案**：一张证书只能代表它
署名的那一台机器，控制面会把请求里自报的 node_id 和证书上的名字对上，对不上就拒。
这是共享口令永远给不出的能力。

但**「他该听到多少」这个问题没有变**：一张任意节点的证书，读到的仍然是全平台的明文。
区别在于取得这张证书的成本 —— 从前是「拿到任何一份配置文件里都抄着的那个字符串」，
现在是「拿到某一台机器上的私钥」。**这是真实的提升，但不是隔离。**

因此，凡是对外描述安全态势的文字，都不能把这一轮写成「一台节点被攻破只影响它自己」。
准确的说法是：**一台节点被攻破，仍然等于全平台租户的明文**；变化的是别人不再能靠
一个到处都是的共享字符串走到这一步。

### 修的方向

按 ADR-025 的 M2（能力券），清单应当只回答调用方名下确实被分配到的那些环境，
密钥值按环境单独授予。这需要控制面知道「哪些环境分配给了哪台节点」—— 目前
`list_assignments()` 没有这一维，所以这不是加一个 `filter` 能解决的，要先有分配关系。
在那之前，节点私钥的保管等级应当按「等同于控制面主密钥」对待，
`docs/trust-boundaries.md` 已按这个口径改写。
